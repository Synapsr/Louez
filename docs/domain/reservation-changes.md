# Reservation changes

What changes a reservation once it exists: its status, made by any actor, and its shape (dates, lines, prices, delivery), made by the store's edit. This page is the specification of the lot that moves these writes to one service per kind of write in `packages/api`, on RPC, OpenAPI and MCP. It states what the code does today, the rules the lot proposes, the options those rules introduce, and how to slice the work. The rules every writer holds are in [Reservation invariants](reservation-invariants.md); the words are in the [glossary](glossary.md).

Every sentence about the code is true at `origin/rental-core` 3b011bfc and cites where. A sentence that proposes is marked **Proposed**; a choice nobody has made yet is marked **To decide**. Line numbers drift: search the quoted name when one no longer matches.

Two standing rules frame every proposal:

1. **No dead end for the store.** A store-side refusal on returnable stock or on the turnover buffer always has an explicit override, recorded with the write. A customer, a payment, the marketplace and the system never get that choice. Consumable stock and a unit's hard conflict have no override (S3, S4).
2. **Named rules, today's defaults.** Each business rule is a named function with parameters, whose default is what the code does today, so a store, a product or a channel can later get its own value without new logic. An option exists only where a case in the code or the invariants needs it.

## 1. The writers, as the code is today

`changeReservationStatus` (`packages/db/src/reservation-status.ts:264`) is under every status change. It locks the reservation row (`:272`), plans the change from the locked status (`planReservationStatusChange`, `:190`), asks the card gate for a change into `confirmed`, `ongoing` or `completed` from outside them unless the actor is `payment` (`:286`), runs the caller's `beforeWrite` (`:291`), moves consumable stock (`:293`: `consume` from `pending` or `quote` to `confirmed`, `restore` from `confirmed` or `ongoing` to `cancelled` or `rejected`, `:180`), writes the status and its dates, writes one activity row (`:314`) and marks the billing snapshot (`:320`). It returns the fee effects; the caller runs them after the commit. Consumable stock locks the consumable products of the reservation, after the reservation (`packages/db/src/consumable-stock.ts:220`).

`checkExistingReservationInventory` (`packages/api/src/services/reservation-inventory.ts:666`) is the stock check of a change into `confirmed`. It locks the reservation's products (`:697`), runs `reserveInventory` with the turnover buffer, without the consumable check (`:716`), with the required-accessory check (default `skipRequiredAccessoryCheck = false`, `:185`) and with `onShortfall: "fail"` (default, `:186`), then checks each held unit by id (`findReservationUnitConflicts`). A unit's hard conflict throws `ReservationUnitConflictError` (`:725`); any failure of `reserveInventory`, a missing required accessory included, throws `ReservationInventoryError("errors.productNoLongerAvailable")` (`:727`); a buffer-only conflict refuses nothing and is returned as `turnoverBufferOnlyUnitIds` for the activity row (`:733`).

No hand-written MCP tool writes a status: `packages/mcp/src/tools/` holds calendar, customers and payments only. The holds of the marketplace create a booking through the checkout's `createReservation` (`marketplace-booking.ts:700`) and change no status.

Where the status writers differ:

- **Lock order.** The store's path locks products before the reservation. The customer's acceptance, the paid confirmation and the marketplace's cancellation of a confirmed booking lock the reservation first, then products, and rely on deadlock retries (C1). The other paths move no stock and lock no product.
- **Override.** No status writer can book over returnable stock; the store's dashboard creation and edit can (S3).
- **What a confirmation records.** Only the dashboard's creation and edit write a capacity verdict (`apps/web/app/(dashboard)/dashboard/reservations/actions.ts:1077`, `:2886`); a confirmation writes `turnoverBufferOnlyUnitIds` and nothing about the stock.
- **Required accessories.** The dashboard's creation and edit skip them (`actions.ts:942`, `:2872`); every confirmation checks them (`reservation-inventory.ts:185`). A quote the store typed without a required accessory, or a request whose accessory line the store removed, is refused at every confirmation as "no longer available", by the store, the customer and the payment alike.
- **Effects.** The store's changes queue outbox rows in their transaction; the customer's, the payment's and the marketplace's send from memory after the commit (E1).
- **Insurance.** The store's confirmation creates the Tulip contract through `ports.insurance`; the customer's acceptance and the paid confirmation create none (by reading).
- **Date-change requests.** The store's changes settle them; the marketplace's cancellation does not.

## 3. Open points to close in this lot

### 3.1 A quote or request over the stock cannot be confirmed (S3)

**Defect.** `checkExistingReservationInventory` has no override (`reservation-inventory.ts:186`, `:727`), and `changeStoreReservationStatus` passes none (`reservation-status.ts:507`). A quote created with `allowOverbooking` (`actions.ts:948`; a quote holds no stock, so nothing else refuses it) is refused at its confirmation as long as the shortfall lasts, by the store and the customer. A paid request that lost its stock stays `pending` (`complete-checkout-payment.ts:233`) and the store cannot confirm it either. The store is in a dead end, against S3.

**Proposed rule.** A store-side confirmation (`pending` or `quote` to `confirmed`) runs the stock check with `onShortfall: "collect"`. Shortfalls refuse it with `RESERVATION_INSUFFICIENT_CAPACITY` (`CONFLICT`, not retryable, `details.shortfalls`: product, combination, asked, free), unless the call carries `allowOverbooking: true`; then it is written, and its activity row records the verdict (3.3). A unit's hard conflict and consumable stock below zero are never overridden. The customer's acceptance and the paid confirmation never carry the flag; question 6.1 asks whether a store's earlier approval carries over to a customer's acceptance.

**Option.** `overbookingPolicy(actor, channel)`: `"overridable"` or `"refuse"`. Default today: `overridable` for the dashboard's creation and edit, `refuse` everywhere else. The rule makes the store's confirmation `overridable` on demand; without the flag it refuses as today. Scope: actor (store session; key and agent, question 6.2). Not a store setting yet: no case asks a store to forbid its own overbooking.

**Data.** None new: the verdict goes in the activity row's metadata (`capacityVerdictMetadata`). The input of `reservations.updateStatus` gains `allowOverbooking` (optional, default false).

**Test.** `packages/api/src/routers/dashboard/reservations.db.test.ts`: a quote created over the stock is refused at confirmation with its shortfalls and nothing written; sent again with `allowOverbooking`, it is confirmed, its consumables taken, its row records `overbooked: true` and the shortfalls, and the inbox shows it. The same for a paid `pending` request whose stock went meanwhile. A hard unit conflict is still refused with the flag.

### 3.2 The store's turnover-buffer override is not stored (S4)

**Defect.** The assignment and the move to another unit check `overrideTurnoverBuffer` and store nothing (`actions.ts:4884`, `:4967`, `:4684`; `schema.ts:3290`). A confirmation then cannot tell a buffer conflict the store approved from one that appeared since (a unit given to a quote while free, then another booking placed beside it); it accepts both and names the units (`reservation-inventory.ts:733`). And its stock check still applies the buffer: with one unit, the confirmation of a reservation whose buffer conflict the store approved is refused as short stock (`status-change-races.db.test.ts:414` holds the case with two interchangeable units only).

**Proposed rule.** An assignment made with the override records the approval on the assignment row: who, when. A confirmation, whoever makes it:

- accepts a buffer-only conflict on an approved unit, and names it in its activity row as approved;
- treats a buffer-only conflict on a unit nobody approved as today (accepted and named), and the inbox lists it until the store approves or reassigns (question 6.3 asks whether to refuse it instead);
- runs its stock check without the buffer when, and only when, the check with the buffer fails, the check without it passes, and every buffer-only conflict of the reservation is on an approved unit. The activity row then records `turnoverBufferOverridden: true`.

The store's confirmation may also carry `overrideTurnoverBuffer`, as the edit does (`actions.ts:2867`): it approves every buffer-only conflict it finds, records them, and leaves the buffer out of its stock check. An edit that moves the dates with the override records the approval on the units it keeps.

**Option.** `turnoverBufferMinutes` (store setting, exists) stays the buffer. `turnoverBufferOverride(actor)`: store-side only, per call, never a setting; the stored approval is its trace.

**Data.** Additive migration: `reservation_item_units.turnover_buffer_approved_at` (timestamp, null) and `turnover_buffer_approved_by` (user id, null). The unit event payload of an assignment also gets `overrideTurnoverBuffer: true`, so the unit's history shows it. A new inbox source `unit_buffer_conflict` (read-only, no data).

**Test.** `status-change-races.db.test.ts`, one unit: assigned over the buffer with the override, then confirmed by the store, the customer and the payment (each confirms, row records the approved unit, stock check passes without the buffer); assigned while free, then a booking placed in its buffer: confirmed and listed in the inbox; with the store's `overrideTurnoverBuffer`, confirmed, approved, and the inbox item leaves.

### 3.3 A confirmation records no capacity verdict (S3)

**Defect.** `CAPACITY_VERDICT_ACTIVITY_TYPES` is `created` and `modified` (`packages/api/src/services/capacity-verdict.ts:14`). An overbooking flagged at creation (a quote typed over the stock) stays in the inbox's `overbooking` source (`inbox.ts:1157`) after a confirmation that fit the stock, until an edit writes a new verdict, the reservation ends, or it is cancelled.

**Proposed rule.** Every confirmation that runs a stock check writes a verdict on its own activity row: `overbooked: false` when it fits, `overbooked: true` with the shortfalls when the store overrode. The verdict types become `created`, `modified`, `confirmed`, `quote_accepted`. The verdict row is dated after every earlier row of the reservation (`nextCapacityVerdictDate`), so the latest verdict is never a tie.

**Option.** None.

**Data.** `changeReservationStatus` takes the activity row's date from its caller: today `now` is "tests only" (`packages/db/src/reservation-status.ts:87`) and the row is dated `now` (`:249`). Proposed: `activity.createdAt`, used for the row only (the status dates keep `now`). No migration.

**Test.** `packages/api/src/routers/dashboard/inbox.db.test.ts`: a quote created over the stock shows an `overbooking` item; the stock is freed; the store confirms; the item leaves. Same through the customer's acceptance and the paid confirmation.

### 3.4 Paths that lock the reservation before its products (C1)

**Defect.** `acceptQuote` (`.../actions.ts:200`, `:207`), `confirmPaidReservationOrThrow` (`complete-checkout-payment.ts:174`, `:181`) and `cancelMarketplaceBooking` (`marketplace-booking.ts:1133`, restoring consumables) lock the reservation in the helper, then products, and retry a lost deadlock (`retryTransactionOnDeadlock`). The extension and the unit assignment do the same with one retry (`extension-quote.ts:53`, `:176`; `actions.ts:4701`, `:5038`). No test fails when a new path inverts the order.

**Proposed rule.** One function locks for a change: `lockReservationForChange(tx, reservationId, storeId)`, today's `lockReservation` of the store service (`reservation-status.ts:179`) without its preview reads: the reservation's products by id, the reservation, and a restart when a product joined meanwhile. It returns a lock token. `changeReservationStatus` takes the token for a change that moves stock or runs a stock check (`consume`, `restore`, or a `beforeWrite`), and throws without it; its own `FOR UPDATE` then finds the row already held. Every status writer moves to it; the deadlock retries stay as a guard, the products-changed restart becomes their main use. The extension and the assignment move with the shape lot (3.6), not here.

**Option.** None.

**Data.** None.

**Test.** `scripts/reservation-writes.test.mjs` fails on a call of `changeReservationStatus` that moves stock without a `lock`; the status-change races (`status-change-races.db.test.ts:613`, `:641`) run without a single deadlock retry (count the retries in the test). C1 moves to Held for status changes.

### 3.5 Messages after the commit, not through the outbox (E1)

**Defect.** `acceptQuote` sends the store's notification and `customer_quote_accepted` from memory after the commit (`.../actions.ts:282`, `:331`); `declineQuote` and `cancelReservationRequest` the store's notification (`:449`, `:582`); the paid confirmation its three messages (`complete-checkout-payment.ts:394`, `:482`, `:493`); a new booking `customer_request_received` and `reservation_new` (`apps/web/lib/reservations/post-creation-effects.ts:171`, `:205`), and the dashboard's creation its quote and its notifications (`actions.ts:1218`, `:1278`). A crash between the commit and the send loses them.

**Proposed rule.** Every status writer of this lot queues its messages as outbox rows in its transaction, with the snapshot it read under its locks, as the store's path does. New effect types: `reservation.customerMessage` gains `customer_quote_accepted` and `customer_reservation_confirmed`; the store's notifications already have `reservation.storeNotification`. A row carries no link the sender must create: the quote acceptance's payment link becomes the reservation's page in the customer account, where the payment is opened (question 6.4). The contract link's access token is minted by the sender, at send time.

The new booking's messages are the creation lot's: they change `createReservation` and `createManualReservation`, which this lot does not touch.

**Option.** None. Which messages go out stays the store's customer notification settings.

**Data.** No migration (`api_effects` exists). Payload types in `ApiEffectPayloads`, senders in `apps/web/lib/api/effects.ts`.

**Test.** For each path: the transaction rolls back after the change (forced error) and leaves no row; it commits and leaves one row per channel, whose payload states the reservation's currency; a dispatch failure leaves the row for the cron.

### 3.6 `updateReservation` moves to `packages/api`

**What it requires.** The function reads outside the package: the session (`auth`, `getStoreForUser`), the Tulip mode, quote and contract sync (`getDashboardTulipInsuranceMode`, `previewTulipQuoteForCheckout`, `syncTulipContractForReservation`), the location snapshots (`apps/web/lib/reservations/location-snapshots.ts`), the delivery fee (`calculateTotalDeliveryFee`, `apps/web/lib/utils/geo.ts`), the edit fingerprint and demand comparison (`apps/web/lib/reservations/util.reservation-edit.ts`), the modification email (`sendReservationModificationEmail`, `actions.ts:3852`), analytics and `revalidatePath`. `getRouteDistance`, `reserveInventory`, the capacity verdict, the contract validation and the date-change requests are in the package already.

Proposed split:

- **Into the package as code**: the fingerprint and demand comparison (pure), the delivery fee (pure), the location snapshot (a read of the store's locations), the pricing of a line.
- **Ports**, until the Tulip integration moves (lot 7): `ports.insurance` gains `quote(reservation, lines, window)` and `syncContract(reservationId)`, both never throwing, a failure being a warning in the answer, as `createContract` is (`platform/ports.ts:401`).
- **Outbox**: the modification email becomes a `reservation.customerMessage` row (`customer_reservation_modified`, a new notification) queued in the edit's transaction when `notifyCustomer` is set; analytics a `reservation.statusAnalytics`-like row.
- **`afterCommit`**: the revalidation (`reservation.updated`).
- **Stays in the app**: the form, and the server action until the page calls the procedure.

**Contract.** `reservations.update`, `POST /reservations/{id}` (`storeProcedure`, `scope: reservations write`, `sensitive: "send"` when `notifyCustomer`, else none). Input: `id`; optional `startDate`, `endDate` (ISO with offset); `lines` (each `id` for a kept line, `productId`, `quantity`, `selectedAttributes`, `unitPrice` and `isManualPrice` for a manual price, `depositPerUnit`); `delivery`; `insurance: boolean`; `notifyCustomer`; `allowOverbooking`; `overrideTurnoverBuffer`. An absent field leaves its part unchanged. Output: the reservation as `reservations.get` returns it, `difference` and `previousTotal` as decimal strings in the reservation's currency, `warnings`, `capacity: { overbooked, shortfalls }`, `links`. Errors, each with a stable code: `RESERVATION_NOT_FOUND`, `RESERVATION_NOT_EDITABLE` (status), `RESERVATION_CHANGED_MEANWHILE` (retryable after a read), `RESERVATION_INSUFFICIENT_CAPACITY` (shortfalls), `RESERVATION_UNITS_UNAVAILABLE` (hard), `RESERVATION_TURNOVER_BUFFER_CONFLICT` (units, overridable), `RESERVATION_TOO_MANY_ASSIGNED_UNITS`, `CONSUMABLE_INSUFFICIENT_STOCK`, `RESERVATION_WINDOW_INVALID`. Confirmation for agents: an edit that changes the total, sends a message, or carries an override answers `CONFIRMATION_REQUIRED` with a preview (old and new dates, total and difference, shortfalls booked over, units approved over the buffer, the message and its channel), bound to the reservation's fingerprint. MCP name `reservations_update`, bundle `daily`. OpenAPI and MCP serve it once the registry lists it, after the behaviour-preserving move is merged and reviewed.

**Invariants on the way**, each its own slice (section 5):

- **T3, editable statuses.** One rule for the procedure and the edit context: `pending`, `quote`, `confirmed`, `ongoing` are editable; `completed`, `cancelled`, `rejected`, `declined` are not (today the action refuses `completed` only, `actions.ts:1806`; the context also `cancelled` and `rejected`, `reservation-edit-context.ts:16`). Tested before and under the lock.
- **T5, a window of no length.** `endDate > startDate`, and a local date and time typed by the store exists in the store's time zone (the extension's round trip, reused). Today: `newEndDate < newStartDate` only (`actions.ts:1830`).
- **M1, totals under the locks.** The edit prices from what it reads under its locks, and the total is `calculateTaxBreakdown` of the lines, delivery and discount, as the checkout computes it (today `subtotal + delivery − discount`, `actions.ts:2525`, and `taxAmount`, `subtotalExclTax` are not rewritten). The fingerprint then guards the lines it did not reprice, not the prices.
- **M3, an edit keeps the booking's pricing facts.** A line the edit does not touch keeps its stored price. A line it reprices (dates moved, quantity changed) is priced by `priceCart` with the product's promotion as stored on the line when the booking was made, and with the tax rate stored on the reservation, not the store's current one. Today the seasonal engine alone, without the promotion (`actions.ts:1980`, `:2128`).

### 3.7 The storefront shows an open choice on the product only (S1)

**Defect.** `getStorefrontAvailability` gives each combination `min(units of the combination − reserved on it, units of the product − reserved on the product)` (`packages/api/src/services/availability.ts:783`). Another booking that left a size open counts on the product, not on the sizes that can serve it: a size it needs can show free, and the checkout, which allocates with `allocateStock`, refuses it. The marketplace (`marketplace-availability.ts:596`), the MCP calendar (`packages/mcp/src/tools/calendar.ts:110`) and the assistant (`apps/web/lib/ai/tools.ts:1036`) count the same way, per product.

**Proposed rule.** What a combination shows free on a window is what `allocateStock` would give one checkout line of that combination: the largest quantity `q` such that a line `{ candidates: [combination], quantity: q, single: true }` fits next to the other bookings at every instant. One rule for the write and the display.

**What it takes.** The display loads what the write loads (`reserveInventory`: the overlapping bookings with their lines, units and choices, the rentable units per combination), builds the bookings' demands with `combinationsServing`, and asks `allocateStock` once per combination with a line of the combination's whole capacity: the served quantity is what is free (`allocateStock` gives the most that fits, by `largestWhere`). Share that loading with `reserveInventory` instead of copying it (ADR 0006). Cost: one allocation per combination of each product shown; a product page shows one product, a listing many: measure on the largest store's listing before turning it on there.

**Option.** None.

**Data.** None.

**Test.** `packages/api/src/services/availability.db.test.ts` (or the existing storefront availability test): a booking that chose the size alone, M, with two colours of M and one other size; the storefront shows the M colour it needs as taken and the other size free, and for each combination the quantity shown is what the checkout accepts and one more is refused.

## 6. Questions for the owner

**6.1 May a customer accept a quote the store created over the stock?** The store booked over on purpose; the customer cannot override (rule 1). (a) Refuse: the customer sees "no longer available" and the store must confirm it itself (slice 3). (b) Accept when the shortfall is no worse than the store approved: for each product and combination, what is missing now is at most what the latest verdict recorded; worse, refused as today. **Recommendation: (b).** The store already decided; refusing makes the customer's acceptance fail on a decision that is not theirs, and makes the store redo it. The data exists (the verdict's shortfalls), and a worse shortfall still refuses.

**6.2 May an API key or an agent book over the stock?** Today only the dashboard can (its creation and edit are not on OpenAPI or MCP). (a) Session only (`meta.actors: ["session"]` for a call with `allowOverbooking`). (b) Keys and agents too, with a confirmation always asked (`requireConfirmation({ always: true })`) whose preview lists every shortfall. **Recommendation: (b).** An agent that runs the store's day would otherwise hit the dead end rule 1 forbids; the always-asked preview keeps a human, or at least the preview, between the agent and a promise the store may not keep.

**6.3 A buffer-only conflict nobody approved, at a customer's or a payment's confirmation: accept or refuse?** Today accepted and named in the activity. (a) Keep accepting, and show it in the inbox until the store approves or reassigns. (b) Refuse, as a hard conflict. **Recommendation: (a).** The buffer is the store's margin between rentals, not a second customer on the unit; refusing would leave a paid booking `pending` over the store's own comfort, and the store can still fix it before pickup.

**6.4 The quote acceptance's message and its payment link.** The link is a Stripe session opened after the commit; an outbox row cannot hold it, and its sender cannot open it safely on each retry (`createReservationPaymentSessionForCustomer` opens a new session on every call, `apps/web/lib/reservations/payment-session.ts:33`). (a) The message links to the reservation's page in the customer account, which opens the payment. (b) The sender opens the session at send time, with an idempotency key per row. **Recommendation: (a).** One more click for the customer, but the amount is computed when they pay, no orphan sessions, and the account page already opens the payment (`.../actions.ts:85`).
