# API and agents

Every action a store user can take in the dashboard is one oRPC procedure in `packages/api`. The same procedure serves three transports:

| Transport | Endpoint   | Credential                     | Caller                                |
| --------- | ---------- | ------------------------------ | ------------------------------------- |
| RPC       | `/api/rpc` | dashboard session cookie       | the dashboard, through TanStack Query |
| OpenAPI   | `/api/v1`  | API key (`Bearer lz_…`)        | scripts, n8n, integrations            |
| MCP       | `/api/mcp` | OAuth access token, or API key | Claude, ChatGPT and other agents      |

`/api/rpc` also requires the header `x-csrf-token: orpc` on every call (oRPC's simple CSRF protection, `apps/web/lib/orpc/csrf.ts`): only script on the app's origin can add it, so no other site, same-site ones included, can call a procedure with the user's cookie. The app's link sends it; a call without it gets 403 `CSRF_TOKEN_MISMATCH`.

No transport holds business logic. Validation, authorization, the logic itself and the audit record live in the procedure, so the dashboard, the API and the agents cannot drift apart.

The migration plan, lot by lot, is in `.agent-docs/plan-api-agents-2026-11-07.md` (local). The list of every capability and where it stands is `packages/api/src/platform/inventory.ts`.

## Writing a procedure

Build store procedures on `storeProcedure` from `packages/api/src/platform/procedures.ts`, never on `dashboardProcedure` (legacy, removed at the end of the migration).

```ts
const create = storeProcedure
  .meta({
    capability: "categories.create", // id in platform/inventory.ts
    scope: { domain: "categories", level: "write" }, // what the connection must grant
    mcp: {
      name: "categories_create",
      title: "Create Category", // English, Title Case
      description:
        "Create a product category. Returns the category; an existing one with the same name is returned as is.",
      bundle: "catalog",
      annotations: { idempotentHint: true }, // the other hints are derived (see The bridge)
    },
  })
  .route({ method: "POST", path: "/categories" }) // its OpenAPI path
  .input(createCategoryInput) // contracts/categories.ts
  .output(createCategoryOutput)
  .handler(({ context, input }) => createCategory(context.actor.storeId, input)); // services/categories.ts
```

The package has four layers. `contracts/<domain>.ts` holds the input and output schemas and the domain's errors, with no database. `services/<domain>.ts` holds the business logic and takes the store id from the actor. `routers/dashboard/<domain>.ts` holds the procedures: contract, rights, confirmation, and a call to the service. `platform/` holds what every procedure shares. Categories (`routers/dashboard/categories.ts`) are the reference.

`storeProcedure` does this before the handler runs, on every call:

1. It checks that the credential is one the transport accepts and that it is still valid. A credential that is present but invalid fails. The procedure never falls back to another credential: a bad token never falls back to the cookie.
2. It checks `meta.actors`. `["session"]` refuses every key and token. Use it for anything that creates, changes or revokes a credential, changes a connection's confirmation setting, or invites or promotes a member, so an agent can never give itself more rights.
3. It checks `meta.platformAdmin`: platform staff, from a session only.
4. It resolves the store and reads the role the user holds there now. A removed or demoted member loses access on their next call.
5. It checks `meta.scope`. The right that applies is the member's role cut down to the connection's scopes. A session has its role only. A procedure without a scope is refused. A domain missing from a key's permissions is `none`. A scope with `anyOf` also opens to a connection that holds one of those domains at the same level; the handler then checks each record against its own domain (the inbox).
6. For a key or a token, it checks that the store's plan has `apiAccess`, through `ports.planFeatures`, and applies the rate limit: 120 calls per minute per connection, counted in the database so every instance shares it.
7. It runs every write (`scope.level: "write"`) through `runOperation` (see below).

The handler reads `context.actor` (user, credential, transport, store id and role), `context.store` (the store row) and `context.ports`.

`accountProcedure` is for calls made before any store is chosen: listing or creating stores, granting an agent. It runs steps 1 to 3, and a key or a token counts on the connection's rate limit. An account procedure declares `meta.account: true`. Without a scope, every connection may call it, and it answers for the connection's own account and stores only (`stores_list`). With one, there is no role to cut it down: the connection's scopes alone decide (`accountRefusal` in `platform/permissions.ts`), a session may do anything on its own account, and a write runs through `runOperation` on the account scope: `store_id` is empty (`ACCOUNT_SCOPE`) in `api_operations` and `api_confirmations`, while keys and tokens stay scoped to the connection. Adding a store (`stores` write) also needs a connection over all the user's stores, present and future: an API key or a grant over chosen stores would never reach the new store, and widening a connection is the user's call, so they get `CONNECTION_BOUND_TO_STORES`. Account procedures check no plan feature: there is no store whose plan to read.

## Contract conventions

These apply to every procedure listed in the exposure registry, which means every procedure an agent or the API can reach.

- **Schemas.** Declare an input schema and an output schema. Output schemas validate and drop fields; they do not transform, because a replayed result goes through them a second time. A procedure does not return `{ error }` as a success: it throws.
- **Errors.** Throw with `apiError` or `platformErrors` from `platform/errors.ts`:
  - `message` is plain English, written for a model or a developer;
  - `data.code` is stable (`CATEGORY_NOT_FOUND`), and it is what callers branch on;
  - `data.retryable` says whether the same call can succeed later;
  - `data.i18nKey` is the dashboard's translation key;
  - `data.details` holds structured facts.

  In the dashboard, `apiErrorKey(error)` from `apps/web/lib/orpc/errors.ts` gives the key to translate.

- **Lists.** Paginate with a cursor, sort in a stable order, and cap the page size. A list that also takes page numbers for the dashboard bounds them for keys and tokens (`reservations.list`: the first 10,000 rows, then `PAGE_TOO_DEEP`, which points to the cursor). A list the procedure reads whole and that grows with the store (a product's units, the reservations of a window, a unit's history) comes a page at a time to an agent, never cut: `answerPage` (`platform/answer-pages.ts`) takes optional `cursor` and `limit` (500 at most) on every transport, gives an MCP caller without a limit 100 items (`ANSWER_PAGE_MCP_DEFAULT`) and a `nextCursor`, and the dashboard and the API every item, as before, unless they send a limit. A page follows an explicit total order, each list's `PageOrder`: a key made of its ordering fields then the item's id (the calendar and a product's reservations by start date, the planning by start date then product, a unit's history newest first, a product's units by identifier). The cursor holds the last key read, and the next page starts after that key wherever the list moved: an item added, removed or reordered in the service's result never makes a page skip the items after it. A cursor the tool did not give answers `INVALID_CURSOR`. MCP clients cap an answer (Claude about 150,000 characters, Claude Code 25,000 tokens) and cut the rest. It pages `reservations_list_calendar_period` and `reservations_get_planning_timeline` (`items`), `products_get_reservation_timeline` (`reservations`) and `products_get_unit_history` (`timeline`); their downtimes, bounded by the units, come whole with every page. A product's answer on MCP (`products_get`, and the product every product write returns) carries its first 100 units by identifier, `unitsTotal`, and `unitsNextCursor`, which `products_list_units` (`GET /products/{id}/units`) takes for the next ones. The MCP bridge pages it (`meta.mcp.answer`), after the call and after a replay alike: the procedure returns, and an idempotency key stores, the whole product, so a key used over MCP and replayed over OpenAPI gives every unit, and the dashboard and the API never see the page fields. `products_update` never deletes a unit for being left out of its `units` list, except from the dashboard: for any other caller (an agent holds a page of the units), the list updates the units it names by id and adds those without one, the others stay, and only `removeUnitIds` deletes (`unitsAfterUpdate` in `services/products.ts`; an id there that is no active unit of the product is `PRODUCT_UNITS_TO_REMOVE_UNKNOWN`, one also sent is `PRODUCT_UNITS_SENT_AND_REMOVED`). Explicit ids, rather than a flag saying a list holds every unit: a flag set on a partial list would delete the rest again. The dashboard's form sends the whole list, which still replaces the active units; deleting units asks a confirmation that names them. Bounded lists stay whole: a photo's versions (20 photos of 50 versions at most), a reservation's lines, payments and history.
- **Money and dates.** Money is a decimal string plus a currency. Dates are ISO 8601 with a time zone.
- **Partial updates.** An absent field is left unchanged; `null` clears it.
- **Links.** A procedure that returns a store, a product, a category, a reservation or a customer gives each one `links` (`contracts/links.ts`): `{ dashboard, storefront? }`, absolute URLs built by the helpers of `platform/links.ts` from `ports.urls`, never by hand. A dashboard link names its store (`?store=<id>`), on a dashboard page or a page of the online store editor (`/online-store/<section>`): both show the browser's active store, so the proxy hands such a page load to `app/api/active-store`. A GET never changes the store, as any site can make a browser follow a link: the active store itself, a store the user may not open and an unknown id all redirect to the same URL without the parameter (the answer never tells whether a store exists); another store of the user redirects to `/active-store`, a page that asks "Open in B / Stay on A". Opening posts a form back to the route, which switches only for a same-origin request (`Origin`, and `Sec-Fetch-Site` when sent; the session cookie is `SameSite=Lax`) and a store the user may open (`switchActiveStore`, the store switcher's check), then redirects (303) without the parameter. Signed out, the user goes through `/login` with the link as callback, then the same flow applies. In the in-app chat, a link to the current store drops the parameter and navigates in the app; a link to another store is a full page load, so no client state of the current store carries over. `storefront` is there only when the public can open the page: the store has finished onboarding and, for a product, it is active. Its description tells the model to give these URLs to the user. The in-app assistant's tools return the same links, and the chat opens a dashboard link in the app and a storefront link in a new tab (`components/dashboard/ai-chat/util.chat-link.ts`). Every reservation a reservations procedure returns (list, detail, counters, calendar, planning, agenda, search, status changes, notes) carries its links, and a customer shown with it the customer's; as the customer is null without customers read, so is its link. A link to another domain's record follows that domain's read right.
- **Tool names.** MCP tool names are `domain_action` and stable. A breaking change gets a new name.
- **Exposure.** Every procedure declares `meta.mcp`: either an exposure, or `{ exclude: "<reason>" }`. Nothing is left out silently. OpenAPI and MCP serve a procedure only once it is in the exposure registry (see below).

## Writes: audit, idempotency, receipts

`runOperation` (`platform/operations.ts`) writes one `api_operations` row per write. It records who made it (user, connection, verified client name), how (transport), what (procedure, target id) and how it ended. That row is the audit trail behind "done by Claude".

A caller may send an `Idempotency-Key` header. MCP tools take an `idempotencyKey` argument and map it onto that header.

- The same key with the same input returns the stored result without running again.
- The same key with a different input fails with `IDEMPOTENCY_KEY_REUSED`.
- A call that arrives while the first one is still running gets `OPERATION_IN_PROGRESS`, which is retryable.
- A key whose call failed may run again.
- A key whose outcome was lost never runs again: either the call went through but could not be recorded, or it stayed `running` past its five-minute lease. It fails with `OPERATION_OUTCOME_UNKNOWN`, and the caller checks the current state.

Keys are scoped per store and per connection. Results are stored only when a key is given, and only as the output schema returns them. A procedure whose output holds a secret declares `meta.secretOutput`: its result is never stored and the key is ignored.

A transport reads `context.receipt.operationId` after the call to give the caller a receipt.

A procedure that calls a provider (Stripe) before its own transaction passes the idempotency key on to the provider. An effect after the commit (e-mail, notification, sync) must never fail the operation once it has committed.

**Retention.** A record holds personal data (its result), and the privacy policy keeps the log of an agent's actions 12 months. The cron deletes a record added and last changed more than 12 months ago less a week, on the database's clock (`purgeOperations`, every minute), so a backlog or an outage of up to a week still keeps the promise: it finds the scopes holding one, reading only the records old enough on both dates, the scope with the oldest such record first (a scope whose old records all changed since takes no turn), then deletes oldest first, in batches of 500 within 5 seconds a run. A record changed since, such as a failed key run again, stays 12 months from that change. Its readers look back less far: the inbox 7 days; a replay reads its key, and a key used again after its record is gone runs again; the setup analytics read the marks of a store still offline ([Setup analytics](#setup-analytics)); a connection's last action is the last record left, so one idle for 12 months shows none. Deleting an account deletes its stores' records.

### The outbox

An effect that must not be lost (a customer's email, a store notification, an analytics event) goes through the outbox, `api_effects` (`platform/effects.ts`), not through `afterCommit`:

- **One row per effect and channel**, added in the write's own transaction (`enqueueEffects`) with everything it needs: recipients, dates, amounts, lines, language. A rollback leaves no row, an edit after the commit changes no message, and a failed SMS is retried without sending the email again. A reservation status change reads what its preview, its confirmation and its rows show once, under its locks, so the rows are the channels the preview announced.
- **Dispatch.** Once committed, the service hands the ids to `ports.dispatchEffects`; the app sends them after the answer, with one sender per effect type (`apps/web/lib/api/effects.ts`). A sender throws when nothing went out (the row is retried) and answers `skipped` when there is nothing to send (the channel turned off, no address, the SMS limit reached): the row is then `cancelled`.
- **Claims.** A sender claims its row in a short transaction with a fresh token: a `pending` row, a due `failed` one, or a `running` one whose five-minute lease expired, while it has attempts left. Only the token holder records the outcome, and a sender checks its claim (`assertClaim`) right before each provider call: a sender whose claim was taken over neither sends nor records. The check also fails when the sender ran out of time, before or during its query.
- **Database time.** Leases, retries, the cron's choice of rows and the retention are dated and compared with the database's clock (`NOW(3)`), never an app server's: a claim reads `NOW(3)` in its own statement once the row is locked (MySQL fixes `NOW()` when a statement starts) and dates the lease from it, and a claim check compares `locked_until > NOW(3)` in SQL. Two servers whose clocks disagree still agree on who holds a row.
- **Timeouts.** A sender gets an abort signal, which fires after two minutes or 30 seconds before its lease ends, whichever comes first, counted on a monotonic clock from just before the claim reads the database's clock, so a slow claim or commit is spent from the lease; a check of the signal (`throwIfAborted`) also fails past that deadline when a busy event loop has held the timer back. It passes the signal down to each provider call (`apps/web/lib/api/effect-signal.ts`): the SMS API, the Discord webhooks, fromHello and PostHog take it as a fetch signal, with their own 30-second limit; web push and SMTP take no signal, so under a sender they run with their own limits (30 seconds for a push; 15 seconds to connect and 45 of silence for an email), and each checks the signal last, right before it starts. The store logo an email embeds is fetched with the signal too, so preparation that stalled past the timeout never sends. A sender that times out does not release its row: its outcome is unknown, so the row and every later row of its key stay blocked until the five-minute lease ends, and only then does it run again. A provider call that cannot be cancelled can thus overlap a retry only after the full lease. Leases are computed with the database's `NOW(3)`, in the session's time zone: the database sessions must run in UTC, as Drizzle's timestamp handling already assumes, or a lease could stretch or shrink by an hour on a daylight-saving change.
- **Retries.** A failed row runs again after 1, 2, 4… minutes, at most 6 hours, and is `abandoned` after 8 attempts, takeovers included; an abandoned row's `next_attempt_at` is then the time it was abandoned, which the inbox shows. The unified cron (`/api/cron`, every minute, beside its other tasks so none of them holds it back) retries the due rows, the rows the first dispatch never took, and the expired claims.
- **Order.** Rows of one ordering key (`reservation:<id>:<audience>:<channel>`) go out one at a time, in the order they were added: a row waits while an earlier row of its key is not done.
- **Superseding.** A status change marks as `superseded` only the unsent customer messages it makes false (`SUPERSEDED_CUSTOMER_MESSAGES` in `services/reservation-effects.ts`):

  | New status                                 | Supersedes the unsent              | Why                                                 |
  | ------------------------------------------ | ---------------------------------- | --------------------------------------------------- |
  | cancelled                                  | acceptance of a request or a quote | the booking it confirms is cancelled                |
  | rejected                                   | acceptance                         | the request was refused after all                   |
  | any other (picked up, returned, confirmed) | nothing                            | an acceptance email and its contract link stay true |

  The store's and the platform's notifications are records of each change, and all go out, in order.

- **Gone.** A row whose store or reservation no longer exists is `cancelled` and its payload cleared, never sent. Deleting an account deletes its stores' rows, and deleting a customer deletes theirs.
- **Retention.** The cron deletes done rows (sent, abandoned, cancelled, superseded) 30 days after they were added; superseded and cancelled rows lose their payload at once.
- **Delivery** is at least once: a sender that dies, or times out, between sending and recording leaves its claim to the end of the lease, and the row runs again. An idempotent replay returns the stored result; the first run's rows are already there, and the cron finishes them.
- **Truthful outcomes.** Each sender awaits the real send and throws when it did not go out: analytics go to PostHog's capture API, whose answer is checked (the SDK's flush swallowed failures); an instance without analytics skips the row.
- **One event per row.** An analytics row carries its event's identity, fixed when the row is added (`analyticsEventIdentity`): a UUID and the write's time, sent as PostHog's `uuid` and `timestamp` on every try, so a retry after a lost answer is the same event, not a second one. Reservation rows added before this carry neither and get the time of sending.

Where the store's own notifications go (the owner's phone, the webhook, the members' devices) and whether the store still wants each channel are read when they go out, not frozen: a webhook or a phone changed since is the one that counts, and the table holds no copy of them.

An effect type is a type and its payload in `ApiEffectPayloads`, and a sender in the app. Reservation status changes, an agent's notes change, a store's creation, its launch, an agent's setup actions ([Setup analytics](#setup-analytics)) and a team invitation's e-mail ([The team](#the-team)) use it; the products' notifications and analytics still go through `afterCommit` (lot 9 moves them).

## Background jobs

Some work runs longer than a client waits for a tool call: an AI photo takes 1 to 6 minutes, and Claude or ChatGPT cut a tool call after one or two. Such a procedure queues a job and answers at once with it; `jobs.get` (`jobs_get`, `GET /jobs/{id}`) reads it. The job lives in `api_jobs` (migration 0098, `platform/jobs.ts`), not in `api_operations` (a row there describes the call, and a call running past its five-minute lease turns `unknown`) nor in the outbox (its timeout and lease are global, its rows run one after the other, and it has no result to read).

- **Start.** The service checks and prices the work under its domain's locks, asks for its confirmation, then inserts the job (`queueJob`) in the same transaction, with what it was started with (`input`, the price frozen), the write that started it (`operation_id`) and who (user, connection, client). Once committed it hands the id to `ports.dispatchJobs`. Its answer is the job, queued.
- **One per slot.** `slot_key` names what a job works on (a product and its photo). `active_slot` is 1 while the job is queued or running and null once it ended, so the unique key (`store_id`, `slot_key`, `active_slot`) holds one active job per slot. Starting the same work again while it runs returns that job, with no new confirmation or charge; another kind of work on the same slot answers `IMAGE_JOB_RUNNING` (retryable).
- **Running.** The app runs a dispatched job after the answer (`after()`), at most two at once per process; a job past that stays queued for the cron. A runner claims the job as the outbox does: in a short transaction, with a fresh token and a lease on the database's clock (`NOW(3)`), 8 minutes (`JOB_LEASE_MS`). Its work is aborted a minute before the lease ends, counted from the claim. The transaction that records the outcome locks the row and checks the token (`lockClaimedJob`): a runner whose claim was taken over writes nothing.
- **Retries.** A job runs at most twice (`JOB_MAX_ATTEMPTS`), takeovers included, and runs again only after a failure that may pass (a provider's outage, a timeout, a crash, a debit that could not be written), a minute later. A failure that will not pass (an empty result, a photo removed) ends it `failed` at once; past its attempts it fails with `JOB_ABANDONED`.
- **The cron** (`/api/cron`, every minute) takes the queued jobs whose wait is over (a new job's first minute is left to its dispatch) and the running ones whose lease ran out (a restart, a deploy), and runs them in the background, never in its own request; then it deletes the jobs ended 90 days ago. Deleting an account deletes its stores' jobs.
- **Reading.** `jobs_get` takes the id and an optional `waitSeconds` (at most 25): it reads the row again every two seconds until the job ends or the time is up, so an agent polls a few times, each call well within any client's timeout. It needs read access to the job kind's domain (`JOB_KIND_DOMAINS`); a job of another store is `JOB_NOT_FOUND`. The answer says the status, when to read again (`pollAfterSeconds`), the usual duration, the result or the error, and the record's `links`.
- **Inbox.** A job that failed for good shows as an item (`image_job_failed` for the photos), until the same work starts again. A success needs no attention: it is no item.

Known limit: a job runs in the web process. A deploy during a run loses that run; the lease then hands it to the cron, up to 8 minutes later.

## Sensitive operations

A procedure that moves money, deletes, sends to a customer or spends credits declares `meta.sensitive`. In its handler, after its checks and before its first write, it calls `requireConfirmation` (`platform/confirmation.ts`). It passes a one-sentence preview and the business `state` the preview shows, such as the amount, the recipients or the record's version.

- A dashboard session, or a connection whose confirmation is turned off (`api_keys.confirm_sensitive = false`), runs directly. The dashboard keeps its own confirmation dialogs.
- Two kinds of action are the exception: `requireConfirmation({ always: true })` (or `checkConfirmation`) asks every key and token, even one whose confirmation is turned off, as the agent alone would otherwise decide to move, give back, erase or spend the store's money, or to take a person's access away. Giving access is not confirmed at all: an agent's invitation waits for an owner's approval from a link, as a token the agent holds proves no human agreed. A dashboard session is still never asked: the user clicked the button. The tools that pass it:

  | Tool                                                         | Why                                                                     |
  | ------------------------------------------------------------ | ----------------------------------------------------------------------- |
  | `record_payment`                                             | records money received or paid back (a negative adjustment)             |
  | `return_deposit`                                             | records a deposit given back to the customer                            |
  | `delete_payment`                                             | erases a payment from the reservation's balance and the billing figures |
  | `products_enhance_image`, `products_remove_image_background` | spend AI credits, when the run has a price ([AI photos](#ai-photos))    |
  | `team_remove_member`, `team_cancel_invitation`               | take a person's access away ([The team](#the-team))                     |

  The other sensitive tools keep the connection's setting, as none of them moves money or takes access away: `stores_create` and `stores_go_live` start or open a billing relationship whose terms the preview shows, but charge nothing; the settings writes (currency, taxes, delivery, booking mode, invoicing) change what later bookings cost; `reservations_update_status` and `reservations_cancel` charge, refund and release nothing (a cancellation says so in its preview). `billing_start_card_setup` and the Stripe onboarding hand a link to the user, who types the card or the identity details: the human is already the one acting. A new tool that charges, refunds or releases money passes `always`.

- Otherwise, the first call does nothing. It fails with `CONFIRMATION_REQUIRED`, which carries the preview and a token valid for ten minutes. The caller sends the same input again with the token in the `Louez-Confirmation` header (`confirmationToken` for MCP tools).
- The token is bound to the actor, the connection, the store, the procedure, the input and the state. It can be used once. If any of these change, the token fails with `CONFIRMATION_INVALID`.

This proves the caller saw the preview. It does not prove that a human approved, because the same agent can make both calls. Human approval, through MCP elicitation or an approval link, comes with the first money procedures.

## Ports

The app lends the API only what is bound to Next.js or owned by the billing service, as one `ApiPorts` object (`platform/ports.ts`). The app builds it in `apps/web/lib/api/ports.ts`, and every handler passes it as `context.ports`. Stripe, e-mail and the other providers are adapters inside the package, not ports.

The effects of a write that the app still owns go through one port, `ports.afterCommit(event)`, called once the transaction has committed: page revalidation (`revalidatePath`), the platform notifications (Discord, fromHello) and the product analytics (PostHog). The service emits a typed `ApiEvent` (`product.created`, `product.updated`, …); the app maps it to its effects in `apps/web/lib/api/after-commit.ts`, revalidating at once and running the rest in `after()`. The port never throws and the answer never waits for it. A domain adds its events to `ApiEvent`.

The deployment's addresses are a port, `ports.urls` (`apps/web/lib/api/urls.ts`): `dashboard(path)` on `NEXT_PUBLIC_APP_URL`, and `storefront(slug, path)` through the app's one storefront builder, so a store subdomain, local path routing (`/<slug>` on localhost) and standalone mode come out as the app's other links do, and a preview deployment links to itself. No domain is written in the package.

Two more ports serve the reservation status changes (`services/reservation-status.ts`): `ports.runReservationEffects` records or voids the pay-as-you-go fee right after the commit (billing), and `ports.insurance` creates or cancels the Tulip insurance contract, a port until the integration moves into the package (lot 7). Both run before the answer and never throw; a failed contract is a warning in the answer, as the dashboard shows it. The customer's message, the store's and the platform's notifications and the analytics event go to the outbox (below); `ports.dispatchEffects` sends them. `reservation.statusChanged` only revalidates the pages.

`ports.newStores` serves the creation of a store ([A new store](#a-new-store)): the pricing terms of a new store and its subscription (billing), its welcome AI credits, the standalone mode, and the referral and sign-up cookies of a dashboard request.

`ports.team` serves [the team](#the-team): the plan's seats for members (billing owns plans) and whether the instance sends e-mail.

Two ports serve the [handoffs](#handoffs): `ports.stripeConnect` lends the app's configured Stripe client, or null on an instance without Stripe (the Connect logic is the adapter `adapters/stripe-connect.ts` and the service `services/stripe-connect.ts`); `ports.billing` reads what the billing pages show and opens the billing card's Checkout (`apps/web/lib/billing/billing-port.ts`, over the billing pages' own functions).

Two ports serve the [background jobs](#background-jobs): `ports.dispatchJobs` runs the jobs a write queued once it committed (`apps/web/lib/api/jobs.ts`), and `ports.productImages` lends the AI photo pipeline and the AI credits (`apps/web/lib/api/product-images.ts`, over `apps/web/lib/ai/image/product-image-run.ts`), until the AI layer moves into the package (lot 7). Tests use `createTestProductImages` (`platform/test-product-images.ts`): no provider is called, and its debit writes a real `ai_credit_debits` row in the job's transaction.

Image storage is a port for now (`ports.storage`, built in `apps/web/lib/storage/api-storage.ts`). The storage client is configured from the app's environment and shared with the dashboard's file routes and the `/files` route. Categories and products upload through it; it moves into the package as an adapter in a later lot. The port only stores, reads and publishes; the upload service in the package decides which keys a store owns.

## Exposure registry

The RPC endpoint serves the whole router to the dashboard. OpenAPI and MCP serve only the procedures listed in `EXPOSED_PROCEDURES` (`platform/exposure.ts`), by router path, such as `dashboard.categories.create`. Each line is reviewed. A procedure enters the list when its contract follows the conventions above.

`createExposure(router, paths)` builds what the two transports serve: the list of procedures, and the same procedures as a router. It throws when a listed procedure:

- is missing, or the path is a sub-router;
- has no `meta.scope`, no input schema or no output schema;
- has no `meta.mcp`, or `meta.mcp` excludes it;
- takes or returns something other than an object;
- uses `idempotencyKey` or `confirmationToken` in its input (the MCP bridge adds them);
- is reserved to a session or to platform staff;
- shares its path or its tool name with another one.

A test checks the app's list against the app's router. Tests build their own exposure from the fixture router in `platform/testing.ts`.

## OpenAPI

`/api/v1` (`apps/web/app/api/v1/[[...path]]/route.ts`) serves the exposed router with oRPC's `OpenAPIHandler`. The handler and the document options live in `platform/openapi.ts`.

- A procedure declares a short REST route with `.route()`: `GET /categories`, `GET /categories/{id}`, `POST /categories`, `PATCH /categories/{id}`, `DELETE /categories/{id}`, `POST /categories/reorder`. Path parameters fill the input fields of the same name. A GET takes the rest of its input from the query string, so a number in it is `z.coerce.number()`. Any other method takes it from the JSON body.
- A procedure without a route is `POST /api/v1/<path with slashes>`, such as `POST /api/v1/dashboard/categories/create`. The body is the input.
- The credential is an API key: `Authorization: Bearer lz_…`.
- A body is at most 2 MiB, or the procedure's `meta.maxBodyBytes` when it takes more (an image's bytes: 8 MiB; a product write: 32 MiB), read streaming before anything parses it; past 2 MiB, only once the key is known (413 `REQUEST_TOO_LARGE`; see [Request bodies](#request-bodies)).
- A write answers with `Louez-Operation-Id`, its receipt. A replayed write also sends `Louez-Replayed: true`.
- An error keeps oRPC's JSON shape (`defined`, `code`, `status`, `message`) with our `data`: `code`, `retryable`, `i18nKey`, `details`.

The spec (`/api/v1/openapi.json`) and a Scalar reference (`/api/v1/docs`) are generated by oRPC, in development only. In production these paths answer 404. The spec documents the bearer API key scheme, the `Idempotency-Key` header on writes, the `Louez-Confirmation` header on sensitive procedures and the receipt headers. Its `operationId` is the tool name.

## Uploads

A file goes up in three calls, the same on OpenAPI and MCP, or in one call that carries the file (below). The upload service (`services/uploads.ts`) serves every store-owned kind of image; `API_UPLOAD_KINDS` lists the kinds open to the API. Categories expose it as `categories_create_image_upload` and `categories_complete_image_upload`, products as `products_create_image_upload` and `products_complete_image_upload`, the storefront's logos and banner photos as `online_store_create_image_upload` and `online_store_complete_image_upload`.

1. The create-upload procedure takes the type and the size. It refuses another type, a size over the kind's limit and a kind the API does not take. It mints a key in the store's folder for the kind (`<storeId>/categories/<id>.png`) and returns it with one HTTP request to send the bytes, valid ten minutes:
   - a public bucket gives a presigned upload straight to the bucket (`PUT` with headers, or a multipart `POST` with fields), bound to the type and the size limit;
   - a private bucket served through the app (`S3_PUBLIC_URL` is a path) gives `PUT /api/v1/uploads/<token>` (`platform/uploads.ts`). The signed token is the credential, as a presigned URL is: it names the key, the type, the limit and the expiry. The endpoint refuses another `Content-Type`, a body over the limit, and bytes that are not the declared image type.

   Its output holds a credential, so it declares `meta.secretOutput`: it is never stored for a replay.

2. The caller sends the bytes, without its API key.
3. The complete procedure takes the key. It refuses a key outside the store's folder for the kind. It then checks what arrived: the size, the stored type, and the first bytes against the declared type, since a presigned upload never passed through the app. A file that fails is deleted. A good one is made public, and the procedure returns its URL.

The record then takes that URL (`imageUrl`), and its service checks it with `isOwnedImageUrl` against the same folder. The dashboard still uploads through its own file route (`/api/files/<kind>`), which streams with progress.

An agent often cannot send the bytes anywhere but Louez: its sandbox's network allows only the MCP server, and an image it drew lives only there. One call then does the three steps: `categories_upload_image` (`POST /categories/images`), `products_upload_image` (`POST /products/images`) and `online_store_upload_image` (`POST /online-store/images`, with `kind`), on the same capability, scope and rights as the create and complete procedures. Their hints: additive (each upload is a new key, and no record changes until the url is set on it) and open-world as a provider call (an `imageUrl` makes Louez download a public image; the reach is static, so it holds for the bytes too). `uploadImage` (`services/uploads.ts`) takes exactly one of:

- `contentBase64`: the bytes, base64 or a `data:image/…;base64,` URL, at most 5 MB once decoded (`INLINE_UPLOAD_MAX_BYTES`), and the kind's limit when it is lower (a logo: 2 MB). The size is read from the text's length before anything is decoded. An optional `contentType` must match the bytes.
- `imageUrl`: a public HTTPS URL Louez downloads through the guarded fetch of `@louez/auth/guarded-fetch`, the one the OAuth clients' site icons use: the CIMD transport (every DNS answer must be public, the connection is pinned to the checked address, redirects are never followed by it), up to three redirects followed by hand and each checked again, ten seconds per request and per body, and the kind's limit read while streaming (a product: 15 MB). At most four imports download at once in a process (`UPLOAD_IMPORT_BUSY`, retryable). A private address, a redirect to one, plain HTTP, an answer other than 200 or a timeout is `UPLOAD_URL_UNREACHABLE`; it is retryable for a timeout and for the host's 408, 425, 429 and server errors (5xx), and permanent otherwise. A key the upload allocated is deleted when storing, checking or publishing fails; a failed delete is logged as `image_upload.cleanup_failed`, with the first 16 hex digits of the key's SHA-256 and the error's name, code and status only.

The type is the one the first bytes show (JPEG, PNG, GIF or WebP; never SVG), never the declared one alone. The bytes go under a fresh key of the store's folder for the kind, then `completeImageUpload` checks and publishes them as for any other upload, and the answer is the same: the key and the public `url`. Tests mock `@louez/auth/guarded-fetch` with `createTestImageFetch` (`platform/test-image-fetch.ts`): nothing leaves the process.

### AI photos

An agent improves a product photo the way the dashboard does (Téo's decisions, 2026-11-09): `products_enhance_image` (`POST /products/{id}/images/enhance`: GPT Image, then the background cut out and the photo framed 4:3) and `products_remove_image_background` (`POST /products/{id}/images/remove-background`: the cut-out alone). Each takes the product's id and one of its `images`, and starts a [background job](#background-jobs) (`services/product-images.ts`), in the `catalog` bundle, with `products` write.

- **Refusals, before any preview:** the instance lacks the providers (`AI_IMAGE_UNAVAILABLE`), the URL is not one of the product's images (`IMAGE_NOT_ON_PRODUCT`), Louez does not store it for the store (`IMAGE_NOT_PROCESSABLE`; a demo catalog's trusted image is accepted, as in the dashboard), the photo was already processed (`IMAGE_ALREADY_PROCESSED`: a background-free photo may still be enhanced), the photo's versions are full (`IMAGE_HISTORY_FULL`: 50 versions, or a product already keeping the versions of 20 photos, the most it holds, removed photos included), three photos of the store are already processing (`IMAGE_JOBS_BUSY`, retryable), the store has no credit left (`AI_CREDITS_EXHAUSTED`, with the recharge page's link; for an OpenAI client, only that the credits are out, with no purchase prompt or link).
- **Price and confirmation.** The price is the dashboard's: enhancement is billed `AI_IMAGE_ENHANCE_CREDITS`, background removal `AI_IMAGE_BG_REMOVAL_CREDITS` (free by default), both only with the credit layer on. A run with a price asks every agent for a confirmation, even one whose confirmations are off (`always`), with the price, the balance and what will happen, bound to the product, the photo, the operation and the price, not to the balance (another spend would void every preview). A free run asks no one. The price is frozen on the job when it starts: the job is charged exactly that, whatever the tariff or the credit layer becomes before it runs, and a job that started free writes no debit.
- **The result replaces the photo.** Once the job succeeds, the result is in the photo's place in `images` (on the storefront too) and joins the photo's versions in `image_history`, where the original stays. The job's answer carries the photo before (`source`: its URL and its version id) and after (`result`: URL, version id, credits charged), so the agent can show both; `products_use_image_version` (`POST /products/{id}/images/use-version`) with the source's version id puts the original back, and the result's puts it back again. The start names the source's version id; if a dashboard save gave the photo its lineage meanwhile, the finished job answers the id that lineage holds. A version picked meanwhile is replaced in its place; a photo removed meanwhile ends the job `IMAGE_NO_LONGER_ON_PRODUCT`, uncharged.
- **Money.** Nothing is charged at the start, so there is nothing to refund. The debit (`imgenh:<jobId>`, `imgbg:<jobId>`) is written in the one transaction that also puts the result on the product and marks the job succeeded, under the store's, the product's and the job's locks: no debit without a result, no result without its debit, never two debits. Each run stores its result under its own key (`<storeId>/products/<jobId>-<attempt>-ai.webp`, or `-bg.webp`), which no other run writes, so a runner that lost its claim while storing never replaces the result that won; only the winner's URL goes on the product, in that transaction. A run deletes its own file only once it knows no committed result points at it: it wrote its failure itself (the fenced update changed the job's row), or it saw, under the store's lock, its store gone (an account deleted while it ran), or, under the job's lock, its claim lost or its job or product gone. In any other case the file stays, as an orphan beats a paid result pointing at nothing. The winner deletes the files earlier runs left. The transaction that records the result runs READ COMMITTED (`CREDIT_DEBIT_TRANSACTION`, `apps/web/lib/ai/advisor/credits.ts`), as do the dashboard route's image debit and a phone call's debits, each of which reads other rows before it takes the store's credits lock: the month's included credits are summed under that lock and see every debit committed while it waited, with no gap lock on the ledger that a concurrent debit could deadlock against. The store, the product and the job's claim are still read with locks. The AI advisor's and the phone number rental's debits keep the database's default isolation: each takes the credits lock before the first plain read of its transaction (their callers only write, or read with locks, before it). When the result transaction fails without a clear answer (it may have committed with its answer lost, or still be running on a broken connection), the runner settles it in a transaction of its own that locks the job's row, which waits for the first one to end: a job that succeeded with this run's file keeps it and finishes as a success; a job this run still holds gets its failure written under that lock, so the first transaction can no longer succeed, and only then is the file deleted; anything else, or no answer from the database, keeps the file. A store whose credits run out while its jobs run may go below zero by at most three runs' price, as the dashboard lets one image go below.
- **Versions.** `products_get` shows each photo with its versions (`imageVersions`: id, url, kind, date, the one in use), read from `image_history`, a photo without one as its original alone. Agents never write `imageHistory` itself: sending it replaces every version, as the dashboard's form does. The lineage functions are shared by the form and the server (`@louez/utils`, `product-images.ts`).
- **One pipeline.** The dashboard keeps its own route (`/api/ai/product-image/enhance`: the form holds the result until the user saves), and the route and the job run the same steps (`apps/web/lib/ai/image/product-image-run.ts`): where the source is, the price and the gate, the pipeline, the stored result, the debit, then the auto top-up and the diagnostics. Moving the dashboard onto jobs is the next step (v2).
- **Not for Anthropic's clients.** Anthropic's Software Directory Policy has the server attest that it "does not use AI models to generate images, videos or audio", and `products_enhance_image` redraws the photo with GPT Image: a Claude client never reaches it, whatever its grant (product owner's decision, 2026-11-10; `clientWithholding`, `platform/agent-clients.ts`). It is told apart by a client id on `https://claude.ai/` or `https://claude.com/` (Claude's metadata document) or by a declared name matching "Claude", which, as for OpenAI, only takes a tool away. The withholding names the procedure by capability (`ClientWithholding.capabilities`: `products.enhanceImage`), so the tool is never listed and a call answers `NOT_AVAILABLE_TO_THIS_AGENT` before any confirmation or idempotency key, a replay included; the instructions name only `products_remove_image_background`, and a failed enhancement in the inbox lists `jobs_get` alone. `products_remove_image_background`, which cuts the photo out without redrawing it, `products_use_image_version` and `jobs_get` stay. Every other client, and the dashboard, keep the enhancement.

Known limit: a product form left open with an older state saves it back over an agent's change, as for any concurrent product write.

### Request bodies

Both transports read a body streaming and stop at a limit: 2 MiB on `/api/v1` (`OPENAPI_MAX_BODY_BYTES`), 4 MiB on `/api/mcp`. A procedure that legitimately takes more declares it in `meta.maxBodyBytes`, and only its calls may send that much: the upload procedures 8 MiB (`UPLOAD_IMAGE_MAX_BODY_BYTES`, 5 MB of base64 with the call around it), products create and update 32 MiB (`PRODUCT_WRITE_MAX_BODY_BYTES`). The product limit holds a large product, such as 1,000 units with their notes and photos, as UTF-8 or as JSON with every non-ASCII character escaped (`platform/openapi.test.ts` sends both); it is not computed from every input the schema could take. A larger product must be split: create it, then add units in further `products_update` calls (the units left out stay), or fill each unit's notes, price and date with `products_update_unit_details`. A body past a route's limit gets 413 with a message that says so.

- `/api/v1` matches the request's method and path against the routes of those procedures (`routeBodyLimits`, path parameters included), before parsing. Past 2 MiB (declared, or once that much was read), it first checks the API key or access token from the headers: an anonymous or refused caller gets 401 once 2 MiB have been read (plus the one chunk that crossed that mark, which is never kept), or before any read when its Content-Length is larger. A known caller then takes one of the process's four places for a large read (below). Past the route's limit, declared or sent, the answer is 413 `REQUEST_TOO_LARGE`.
- `/api/mcp` knows which tool a request calls only once it is parsed, so it reads up to the largest limit of its tools, counting four calls on the connection's rate limit for each 4 MiB read past the first, before reading on (see [MCP](#mcp)); a connection without them left gets 429. The request is then served only as a single call to a tool whose limit covers it; anything else past 4 MiB gets 413, with a message that points to `imageUrl` for images.
- Large reads of both transports share four places in the process (`MAX_LARGE_BODY_READS`, `platform/large-bodies.ts`): a request takes one when its body passes its transport's default, after its caller and rate limit are checked, and gives it back once it is answered. With none free, the answer is 503 `LARGE_BODY_BUSY`, retryable, with `Retry-After: 1`. A body within the default never takes a place.

## Migrating a domain

The steps a domain lot follows, as categories did (lot 0c):

1. **Inventory.** List the domain's capabilities in `platform/inventory.ts`: every server action, route, procedure and hand-written tool that does one. A capability the plan adds gets its line too.
2. **Contract.** Write `contracts/<domain>.ts`: input and output schemas (no transform in an output), a list with a cursor and a cap, partial updates (absent leaves, `null` clears), and the domain's errors with stable codes and the dashboard's `i18nKey`.
3. **Service.** Move the logic to `services/<domain>.ts`. Every query filters on the actor's store. Every write that reads then writes takes the same lock, deletions included: the store row (`SELECT … FOR UPDATE`) serializes the domain's writes of one store. A sensitive write computes its preview and asks for the confirmation under that lock, so what the preview shows is what happens. The confirmation's state also binds what the preview may not show, such as where a message goes (a hash of each channel and its address), so a change there voids the token. A write whose checks read what reservation writers change (stock, units, assignments) also takes the rows they lock, in the codebase's order (store, products, reservations, units; [DL-12](../code-review/04-data-layer.md)), before its first plain read: InnoDB reads at the snapshot of that first read, so a lock taken after it would hide a reservation committed while waiting. Keep every effect of the old code, and list them in the PR.
4. **Procedures.** One `storeProcedure` per capability in `routers/dashboard/<domain>.ts`: `meta` (capability, scope with the member permission, MCP name `domain_action`, a title, a description for a model, bundle, a write's `effect`, a `reach` when it has one, `idempotentHint`), `.route()`, schemas, and the service call. A procedure that also shows another domain's records (the product timeline shows reservations and customers) checks those domains too, with `allows()` on the actor's role and scopes, and its description says what it needs. A deletion or another sensitive action declares `meta.sensitive` and calls `requireConfirmation` with a preview that says what will happen and a `state` bound to what the preview shows.
   A domain whose records show another domain's data decides, for a caller without that domain's read, between leaving the data out and refusing. Reservations leave the customer out: a connection with reservations but not customers gets every reservation answer (list, detail, counters, calendar, planning, agenda, search) with the customer, the billing identity, the delivery and return addresses, and every free text that may name them (the team's and the customer's notes, the activity descriptions and details, payment notes) null or empty, and a search by name matches the number only. Payments are left out the same way: without payments read, a reservation comes with no payment rows and no Stripe ids, its payment and deposit entries have no description, every history entry keeps only the details its type lists as free of payment data (`PAYMENT_FREE_ACTIVITY_KEYS` in `services/reservations.ts`), and the payment-method filter is refused (`PERMISSION_DENIED`, payments:read); it keeps `rentalPaid`, what was paid toward the rental, as the dashboard's list shows a paid status to anyone who reads reservations. A cancellation's preview also shows what was paid, for the same reason. The product timeline and history refuse instead (`PERMISSION_DENIED`), as each of their rows is a booking.
5. **Exposure.** Add the paths to `EXPOSED_PROCEDURES` and mark the capabilities `migrated: true`. The exposure test then checks that every migrated capability is served and that every served procedure is in the inventory.
6. **Old paths.** Delete the hand-written MCP tools and the server actions of the domain. Other callers go through the procedures too, never the service: the in-app AI assistant calls them with a server-side client bound to the user's session (`AIChatContext.api`, built in `apps/web/app/api/chat/route.ts`), so its rights are the dashboard's. A migrated capability may keep only a route that serves the browser.
7. **Dashboard.** Call the procedures through the options factories of `apps/web/lib/queries/<domain>.queries.ts`. Show errors with `apiErrorKey`. Keep the dashboard's own confirmation dialogs: a session never gets `CONFIRMATION_REQUIRED`.
8. **Tests.** On the database: each procedure from a session and from a key, the partial update, the confirmation (preview, token, a state change that voids it), another store's ids (not found), a member without the permission, idempotent retries. Through the real handlers: the same calls give the same results and error codes on RPC, OpenAPI and MCP (`packages/mcp/src/categories.db.test.ts`). The OpenAPI test checks the routes.
9. **Agents.** The procedure replaces the hand-written tool, under the new name only: no former name stays callable. Every tool an agent can call is listed (the Claude and ChatGPT directories review what is listed, and OpenAI refuses operations served without being exposed for review), and MCP clients read the list again when they connect. The PR names the tools that changed for MCP users: old name, new name, what differs. The 19 former names that were kept as hidden aliases until 2026-11-09 (`get_store_settings`, `list_products`, `update_reservation_status`…) answer "not found"; the conformance test lists them.

## MCP

`/api/mcp` (`apps/web/app/api/mcp/route.ts`) serves Streamable HTTP with the official SDK v2, statelessly. No session is kept between requests.

- Every request resolves its own context (`packages/mcp/src/auth/resolve.ts`): the key or the access token and its grant, the store and the role held there now, and the plan's API access. A revoked key or grant, a removed member or a lower role applies on the next request.
- A request that fails there never reaches MCP. It gets the platform's error as JSON, with its HTTP status. A 401 carries `WWW-Authenticate: Bearer` with `resource_metadata`, where an MCP client starts OAuth, and `error="invalid_token"` when a token was sent.
- Each request gets a server built for it. GET and DELETE answer 405: there is no session to stream on or to close.
- Rate limiting is the shared limiter. A tool call counts once, where it runs. Every other request counts at the door. A connection that used up its window is refused (429) before its body is read; a body refused at the door (too large, not JSON) counts as a call, and each 4 MiB read past the first counts as four (`OVERSIZED_BODY_WEIGHT`) before the rest is read ([Request bodies](#request-bodies)).

### The bridge

`packages/mcp/src/bridge.ts` makes one tool per exposed procedure.

- The name, title and description come from `meta.mcp`. The arguments are the input's JSON Schema; `outputSchema` is the output's, converted the same way (dates as `date-time` strings).
- Every tool carries `readOnlyHint`, `destructiveHint` and `openWorldHint` as explicit booleans, which the Claude and ChatGPT directories require, and which ChatGPT checks against what the tool does. `mcpToolAnnotations` (`platform/meta.ts`) gives them from what `meta.mcp` says the tool does, never from `sensitive` (a confirmation is about the user's agreement, not about the data):
  - `readOnlyHint` when `scope.level` is not `write`.
  - `destructiveHint` when a write's `meta.mcp.effect` is not `additive`. Both directories mean "may overwrite or delete data already there", whether or not it can be undone. `additive` is a write that only adds and never replaces or clears anything (a new record, a new upload, a payment row, an existing record returned unchanged); `overwrite` is any update, reorder, status change, or link that replaces the previous one; `delete` removes records. The registry refuses a write without `effect` and a read with one.
  - `openWorldHint` when `meta.mcp.reach` is set: the tool reaches outside the user's Louez account. `customer`: it sends a customer a message (required with `sensitive: "send"`). `provider`: it calls a third party (Stripe, the insurer, the company registry), reads included (`billing_get_status` reads the store's Stripe subscription). `public`: it changes what visitors of the store's online store see once it is online, since that is content published on the open web: the catalog, on the storefront and in the marketplace catalogue Louez exports (products, their status, prices, seasons, images, categories and their order, and the variants: which are on, their labels, their values and swatches; deleting a variant counts too, since the export also matches a variant by its label), availability (units, downtimes), the store's texts, contact, address, look and web address, the booking rules, hours, delivery and pickup points, taxes and currency, the legal texts and identity, and going live. A write the public never sees (notes, a unit's purchase details, an upload not yet set, a new store still offline, a draft copy, the inbox) has no reach.
  - `meta.mcp.annotations` carries only `idempotentHint`. The conformance test lists the expected class of every listed tool.
- A description says what the tool does, takes and returns. It never tells the model to call another tool (the Claude directory's rule): how the tools chain is in the server's instructions (`packages/mcp/src/instructions.ts`). It may name another tool as a fact ("its units are in products_get").
- Each tool's `_meta.securitySchemes` is `[{ type: "oauth2", scopes: [] }]`, ChatGPT's per-tool declaration: what a connection may do is its grant, not an OAuth scope. An instance without OAuth declares none.
- A write (`scope.level: "write"`) takes an optional `idempotencyKey`. A sensitive procedure takes an optional `confirmationToken`.
- The tool calls the procedure with `transport: "mcp"` and new headers: the request's `Authorization`, `Louez-Store` set to the request's store, `idempotency-key` from `idempotencyKey`, and `louez-confirmation` from `confirmationToken`. The procedure validates the input, so a bad input fails as it does on the other transports.
- On success, `structuredContent` is the output as JSON (dates as ISO strings). A text block says it is done, gives the output's `links` on a line of their own when it has some, and repeats the JSON, which the MCP specification asks for compatibility (SHOULD) and every client reads. For an OpenAI client the text leaves the JSON out (`credential.structuredContentOnly`, `modelReadsStructuredContent` in `platform/agent-clients.ts`): OpenAI documents that ChatGPT and Codex give the model `structuredContent` ("concise data the model can inspect and use in later calls"), so the copy would only double the answer. Claude's clients document nothing of the kind, so their text keeps it. A write puts its receipt in `_meta`: `io.louez/operationId` and `io.louez/replayed`.
- On failure, the result has `isError: true`. Its text gives the message, `code`, `retryable` and the details; `structuredContent.error` holds the same facts. `CONFIRMATION_REQUIRED` spells out the preview and the token, and tells the model to ask the user, then call again with the same arguments and `confirmationToken`. An error that is not the platform's (a server error, an exception) never shows its message: the tool says Louez hit an unexpected error and what to do, and the error is logged, redacted (`logProviderError`). An older service that throws a dashboard translation key (`errors.productNotFound`) answers in English with the way out (`packages/mcp/src/utils/error-messages.ts`, which a test keeps in step with every key packages/api throws); a key with no message yet is made readable.
- A call that fails with `UNAUTHENTICATED` or `CREDENTIAL_NOT_ACCEPTED` (the token expired or its grant was revoked after the request's check) carries `_meta["mcp/www_authenticate"]`: the 401's challenge with `error="invalid_token"`, from which ChatGPT asks the user to sign in again. A refusal of rights gets none: signing in again keeps the same grant, which only the user changes, in Louez.
- `account_get_profile` (`dashboard.account.getProfile`) is the account's profile tool, `_meta["openai/profile"]: true` (`meta.mcp.profile`): read-only, no argument, it returns the user's id, stable, and the name they gave Louez, left out (never null) when they gave none, as ChatGPT's profile schema takes it; never the e-mail. ChatGPT tells the user's accounts apart by it.
- `serverInfo` names Louez with a title, a description, the app's URL and its icons.

`tools/list` shows only the tools of the connection's bundles that it may call: the member's role cut down to the connection's scopes. The list only shows. Every exposed tool can still be called, and the procedure authorizes the call, so a refusal says `PERMISSION_DENIED` instead of "not found". `packages/mcp/src/tool-registry.ts` serves the list and the calls, because the SDK cannot show a subset of what may be called.

### Stores, tool bundles and instructions

- **Stores.** A connection over several stores (an OAuth grant) names the store of each request: the `Louez-Store` header, or the `storeId` argument every store tool then takes. A grant over all stores takes `storeId` even while it reaches one, since it may create another. A grant that reaches no store yet still connects: the account tools run, the store tools are listed as for an owner and answer `NO_STORE_YET` (a grant over chosen stores that lost them: `NO_STORE_ACCESS`), and resources and prompts are not served. The handler reads `storeId` from the tool call before the context is resolved, so hand-written tools get it too. Without one, the tools are listed, a call that needs a store answers `STORE_REQUIRED`, and resources and prompts are not served. A `storeId` the connection does not reach answers `NO_STORE_ACCESS` from the tool, not from the door. `stores_list` (an account procedure) needs no store.
- **Bundles.** `meta.mcp.bundle` says which bundle a tool is in (`daily`, `catalog`, `settings`, `integrations`, `team`, `billing`); a hand-written tool's bundle follows its domain. `tools/list` shows only the bundles of an OAuth grant; an API key lists every bundle. A tool outside the bundles is still callable: the bundles only show, the scope authorizes. An account tool (`account_get_profile`, `stores_list`, `stores_check_slug_availability`, `stores_create`) is listed whatever the bundles, when the connection may call it. A bundle that holds no listed store tool (`bundlesWithTools` in `platform/exposure.ts`, read from the exposed procedures) is offered nowhere: not on the consent page or the connection editor (`dashboard.agentConnections.getAuthorization` and `list` answer `offeredBundles`, and a grant's bundles among them), not in the instructions. A grant keeps such a bundle stored, so it shows again, with no change, once a procedure of that bundle is exposed: a save from the editor and a new consent keep the bundles the page did not offer (`savedBundles` in `services/agent-grants.ts`), and drop only an offered bundle the user unticked.
- **Instructions.** ChatGPT may read only the first 512 characters, so the instructions open with the essentials: what Louez is, which store the connection acts on (`stores_list` first when it covers several), the `links` to hand on and never to build, and the confirmations. The details follow. They name the store, the bundles listed and those that are not (only bundles that hold a tool), and say that the user enables a bundle in Louez (Settings > Integrations > MCP > Connected agents, with that page's URL), never the agent. With no store yet, they say how to create one (`stores_check_slug_availability`, then `stores_create`), or, for a connection that may not, that the user creates it or connects the agent again with "Read and edit" rights. They say that `team_invite_member` creates nothing: the user approves the invitation from the link it returns, and `handoffs_get` says when; that a removal and a cancelled invitation always confirm; and that sending an invitation again or sharing its link is the user's, on the team page whose link `team_list_members` returns. They also say that records come with `links` to give the user as they are, that the agent never builds or guesses a Louez URL, that a step only the user can take comes as a link to give them, then `handoffs_get` says where it stands ([Handoffs](#handoffs)), and that an AI photo asks the user before spending credits, runs in the background (`jobs_get` reads it; the same photo started again returns its running job), and ends with the before and after images to show the user, undone with `products_use_image_version` and the original's id ([AI photos](#ai-photos)). They describe what tools do and what is enough, conditionally, never a schedule or an order aimed at the model ("call it every 5 minutes", "never open it"), which a directory reviewer can read as prompt injection; the description rule above applies to them too.

### Hand-written tools

The tools, resources and prompts written before the bridge stay until their domain moves to procedures. They are served with the same metadata as the procedures: `legacyTool` takes a name, a title and, for a write, its `effect` (and a `reach` when it has one), derives the three hints as for a procedure, and answers a bad argument with `INVALID_ARGUMENT` and its issues; a business refusal (`toolError`) has a code (`NOT_FOUND`, else `REQUEST_REFUSED`). They return text only, so they declare no `outputSchema`. They already sit behind the same boundary: the per-request context, `requirePermission` with the role cut down to the scopes (a missing domain is `none`), the plan check and the shared rate limit. Their platform errors answer in the bridge's format. The customer and payment tools give the dashboard links of what they show in their text, through the same helpers; a link to another domain's record only when the connection may read that domain. Those that move money or delete (`record_payment`, `delete_payment`, `return_deposit`) declare `sensitive` on `legacyTool`, with `always`, as they move money ([Sensitive operations](#sensitive-operations)): they take `confirmationToken` and run through `requireConfirmation` before their handler, whatever the connection's confirmation setting, with a preview of the call and a state read from the record (its status, the amounts, the counts it would delete), under the procedure name `mcp.<tool>`. A call that takes none of a tool's sensitive paths runs directly.

Known limit, accepted until these tools become procedures (lot 2c for payments): the confirmation's state is read and its token checked before the handler, outside the transaction it writes in, so a change landing between the check and the write is not caught. A procedure asks for its confirmation under its domain's lock, inside the write.

## A new store

`stores.create` (`stores_create`, `POST /stores`) creates a store owned by the caller. The onboarding's store step calls it, over RPC, when `stores.updateOnboardingInfo` finds no store to finish; an agent calls it on MCP. Called from a dashboard session, its answer sets the new store as the active one and spends the referral cookie (`ports.newStores.onboardingCookies`, through oRPC's response headers, which only the RPC endpoint has). One implementation, `services/store-creation.ts`, does what the onboarding always did, in one transaction under the user row's lock:

- the store with the onboarding's default settings (payment mode, one hour minimum, a day's notice, no buffer, the default business hours), its country's time zone, a referral code of its own, and `onboardingCompleted` false: it is offline until the user launches it;
- the owner's membership;
- the referral attribution and the sign-up origin, read from the cookies of a dashboard request (`ports.newStores.signupAttribution`); an agent's store is attributed to no one;
- the billing marks of the store and its legacy snapshot, and the subscription (`ports.newStores.subscribe`): once the store row exists, the billing code decides through the transaction whether Louez bills it, writes its row then (pay-as-you-go with the offer for new stores, the referred welcome gift included), and returns the terms of that one decision;
- in the outbox: the welcome AI credits (`store.welcomeCredits`, the amount `ports.newStores.welcomeCredits` gives at the creation, frozen in the row; none while the credit layer is off) and the analytics events (`store.creationAnalytics`: the referral attribution, the referred reward when the store got one, the store info saved).

The web address is checked first (`stores.checkSlugAvailability`, which suggests free ones close to it); one taken meanwhile fails on the unique key as `STORE_SLUG_TAKEN`, with suggestions. A standalone instance with a store online refuses another one. A key or a token creates `STORE_CREATION_DAILY_LIMIT` (3) stores per account in 24 hours at most, counted on the database's clock under the user row's lock; a session has no cap. The creation is sensitive (`money`): it starts a billing relationship, so an agent first gets a preview with the name, the future public URL, the country, the currency and the pricing that applies, as the billing code says it for a store created now (`ports.newStores.previewTerms`: none on an instance without platform billing, Louez's pay-as-you-go ladder, or the billing service's offer label), bound to the confirmation's state. The preview comes before the store exists and before the creation's lock: the creation compares the terms `subscribe` returns under that lock with the ones confirmed, and when they differ (a billing cutoff passed while it waited) it rolls everything back with `STORE_TERMS_CHANGED`, so the caller asks for a new preview. A caller that runs directly gets the terms in force, and the answer always shows the terms of the decision. The answer holds the store's id, its dashboard link (no storefront link while it is offline), the future public URL, the pricing and the next steps an agent can take with tools that exist today.

`stores.updateOnboardingInfo` (session only, no MCP tool: agents set the same fields with the settings procedures) is the store step on a store the user already has: the one it edits (the user must own it, or be platform staff), else the active store when it is an incomplete store of theirs, else their incomplete store, the one with this web address first; it answers `id: null` when there is none. Under the store row's lock it saves the name, the web address, the contact and the place, the country and the currency, and the onboarding's default rules where the store has none, keeping what the user or an agent set since; for an incomplete store not referred yet, the referral attribution and, when Louez's own billing bills it, the referred reward (`ports.newStores.rewardReferredStore`, in that transaction); in the outbox, the referral events and `onboarding_store_info_saved`. A web address held by another store answers `STORE_SLUG_TAKEN`. Its answer sets the store as the active one and spends the referral cookie it read.

A human who opens the dashboard of an agent's store lands in the onboarding wizard, which resumes that store (the dashboard sends every store whose onboarding is not completed there, and the store step saves it through `stores.updateOnboardingInfo` instead of creating one), prefilled with what the agent filled in. The account's own steps (profile, acquisition source) belong to that wizard and never gate the dashboard itself: once a store is online, the dashboard opens whether or not they were answered. The agent can also put the store online itself ([Going live](#going-live)).

## Going live

A store is online when `onboardingCompleted` is true: the storefront answers 404 before that, and every link to it is left out. `stores.getLaunchChecklist` (`stores_get_launch_checklist`, `GET /stores/launch-checklist`) says what the store still lacks, and `stores.completeOnboarding` (`stores_go_live`, `POST /stores/go-live`) puts it online. Both are store procedures in `routers/dashboard/stores.ts`, the logic in `services/launch.ts`, the tools in the `daily` bundle beside `stores_create`, so a grant with the default bundle sees them right after it creates a store. The server's instructions point to them while the request's store is offline, and after `stores_create`.

- **The checklist** reads the store row and a few facts of its other tables, and gives each item a status: `done`; `missing` (customers will miss it; a `required` one stops the launch); `optional`; `blocked` (Louez billing refuses new bookings, read-only here: only the user fixes it, in the billing page); `unverified` (in place, but Louez cannot read it to confirm it says what it must: a French legal notice of the store's own). Each item says why it matters, lists the tools that fix it (none when only the user can, such as connecting Stripe) and links its dashboard page. The items: the store info (name, country, currency: `required`), a contact email or phone, an active product priced above zero, categories (optional), where customers collect (the store's address or an active pickup point with several points on, unless delivery is the only way; or delivery to an address, which needs the store's coordinates: `getDeliveryAvailability` from `@louez/utils`, the reading checkout and the booking check share), business hours that leave a bookable day, the terms and the legal notice (`hasRichTextContent`), online payments (missing when the store wants payment mode without Stripe, optional in request mode, which needs none: ADR 0004), the card gate (`readReservationGate` from `@louez/db`) and the logo (optional). It also gives the booking mode the store chose and the one the storefront applies, what the catalog holds (`catalog`: an active product, and one priced above zero, as a free consumable is a valid product), and the first bookings for a caller who may read reservations. The dashboard's home checklist reads the same procedure (`components/dashboard/home/util.setup-steps.ts`); its first-product step counts any active product. Reading needs `settings` read.
- **Only the store info is required**, as it is all the onboarding wizard asks before its last step: a human finishes the wizard before adding a product. Everything else is in the preview, so the user decides.
- **French law, a warning** (Téo's decision, 2026-11-08). A store in France is read as selling to consumers (Louez has no setting for a store selling to businesses only), and French law asks it for terms of sale (Code de la consommation) and a legal notice naming the company name, legal form, SIREN or SIRET, registered office, contact email and phone, publication director and host (LCEN, art. 6). `legalRequirements` (`services/legal-requirements.ts`) lists each field: `known` (in the legal profile or the store's contact), `missing`, `automatic` (the host on Louez Cloud, which the storefront names itself; `ports.hostedBy` reads `LOUEZ_HOSTED_BY`) or `unverified`, with the tool that fills it. The storefront's legal notice page shows the store's own text, or its name, address, email and phone without one; it never shows the legal profile, so the identity belongs in the text, which Louez cannot read. Once the store has a text of its own, every field Louez holds is `unverified` (present in the profile or the contact: check the text states it), as are the publication director and a self-hosted instance's host, which Louez never stores; a field it lacks stays `missing`. So a French legal notice is never `done`: `missing` while a field is missing or there is no text, `unverified` (an item status too) once written. The terms and legal notice items say so. `warnings` carries the warning (what is missing) and the advisory (what to check); the go-live preview puts them first, in its summary and its details, lists the items to check (`toCheck`), and the answer repeats them. They never stop the launch; every field's status is bound to the confirmation.
- **Going live** does what the wizard's last step always did: the onboarding's default rules where the store has none (one hour minimum, no maximum, a day's notice, no buffer), the booking mode it is sent (or the store's own), `onboardingCompleted`, and the store's billing mark; in the outbox, the platform's notice (`store.launchNotification`, Discord and fromHello) and the onboarding's completion event (`store.launchAnalytics`); after the commit, `store.launched` revalidates the dashboard's layout and the storefront's, and drops the storefront's cached theme colour (a visit before the launch cached the default). Payment mode without Stripe is accepted, as the wizard always did: the storefront takes requests until Stripe can charge. It needs `settings` write and `manage_settings`.
- **One lock.** It takes the store row's lock first, then reads the checklist: two launches at once run one after the other, and a product or category write, which takes the same lock first, is either seen or waits. A required item missing answers `STORE_NOT_READY` with the items in `details.blocking`, and writes nothing.
- **Confirmation.** It is sensitive (`money`: once online, bookings start, and Louez bills them): an agent first gets a preview with the public URL, how customers will book, what they will see, and what is still missing or optional, asked under the lock and bound to every item's status, the booking mode and the URL. The preview shows the store as the write leaves it: with the booking mode the call sends, so going live in request mode without Stripe lists online payments as optional, not missing. A product deactivated between the preview and the call voids the token.
- **Twice.** A store already online is not launched again: the answer says `launched: false` with its URL, with no confirmation and no effect. Sent another booking mode (the wizard's payment step again, after a Stripe detour), it changes that mode only, confirmed for an agent, and emits `store.settingsUpdated` (`reservationRules`).

The wizard's branding step saves through `onlineStore.updateAppearance`, the same write as the online store editor's look.

## Setup analytics

PostHog says who set a store up, an agent or a human, what an agent filled and whether the store went live. The events, their properties and the analyses they serve are in [../analytics/store-setup.md](../analytics/store-setup.md); the code is `platform/setup-analytics.ts`.

- **The mark.** A setup write (a procedure of the stores, settings, online store, products, categories or customer fields domains) runs its handler with a scope (`runInApiOperation` from `@louez/db`). When it locks a store row (`lockStoreRow`, which every such write takes first) while the store is offline, it writes that store into its own record (`api_operations.setup_store_id`), in the same transaction, under that lock: the mark commits or rolls back with the write, a launch committed before the lock is seen, and one after it waits. `stores.create` marks the store it inserts. A setup write that takes no store lock of its own, an image upload, whose storage requests must never run under that lock, wraps its work in `withSetupMark` (`platform/setup-analytics.ts`): once the work succeeded, a short transaction takes the store's lock, marks, and releases it. Every upload procedure (`createImageUpload`, `completeImageUpload` and the one-call `uploadImage` of the online store, products and categories) does, and a new one wraps its handler the same way. The online store's say which kind of image (`image_kind`). A write refused with a preview under its lock takes the mark back in the transaction that commits the preview (`unmarkSetupWrite`), and a failed write's record clears it. A go-live marks the store as it locks it, before it puts it online; one that finds the store online marks nothing.
- **An agent's setup action.** Once the write is recorded, a key's or a token's write that marked a store adds one `store.agentSetupAction` row (`agent_store_setup_action`), read from its mark in the transaction that marks the operation succeeded (`recordedEffects` of `runOperation`), inside a savepoint. A failure of the row's own (it cannot be written) is logged and loses the event, never the write. A failure that ended the transaction (a deadlock, a lock wait timeout, the savepoint gone with it) runs the whole record again, three times at most, never the handler; past that the operation is `unknown`, as any lost record. An idempotent replay adds nothing, as it never reaches that point.
- **What it says.** The procedure, who (credential kind, and `agentClientOf` the client or key name: a fixed value from a table, never the name itself, which an OAuth client declares and a user types, so either may hold a person's name), whether a confirmation was accepted (the write spent a token: `checkConfirmation` notes it on the scope), the names of the fields set and cleared, and the facts `SETUP_FACT_KEYS` lists: codes, enums, counts and yes/no, never a value a person typed.
- **The summary.** The launch counts, in its transaction and under the store's lock, every record that marked the store, by credential kind: its creation, the launch itself, and each write committed before, whether or not its record is final yet. A write still waiting for the lock will find the store online and marks nothing. It adds `setup_by`, the agents and the time since the creation to `store.launchAnalytics` (`onboarding_completed`), with who launched. A store whose creation left no mark (created before the marks) is `unknown`. Records go after 12 months ([retention](#writes-audit-idempotency-receipts)): a store launched more than 12 months after its creation counts the marks of its last 12 months, and its creation may read `unknown`. A write outside the API (a dashboard server action not migrated yet, such as the integrations, inspections or Review Booster settings) leaves no mark and counts for no one. `store.creationAnalytics` (`onboarding_store_info_saved`) says who created the store, from the same mark.
- **Privacy.** A test sends personal values, and hostile client names, through every setup procedure and checks no event holds them (`setup-analytics.test.ts`); the senders' test holds each event's property allowlist and fails on any other property or a value that looks like an e-mail or a phone (`apps/web/lib/stores/store-setup-effects.test.ts`).

## Store settings

`dashboard.settings.*` (`routers/dashboard/settings.ts`, `services/settings.ts`, the `settings_*` tools of the `settings` bundle, `/api/v1/settings`) holds what a store needs before it goes live: one read, `settings.get` (`settings_get`), and one write per section: store info (name, description, contact, coordinates), company (country and time zone, currency, billing address), legal texts (terms, legal notice, footer note), reservation rules, business hours and closures, delivery, pickup points (create, update, show or hide) and taxes. Reading needs `settings` read; writing needs `settings` write and the member permission `manage_settings`, as the dashboard's settings pages do. Each answer carries the links of its settings page; legal texts and store info link to the online store editor.

- **Partial writes.** A field left out stays; `null` clears it. The business hours take days by name (`monday`…`sunday`, stored as 0 to 6 from Sunday); their closures are replaced as a list, and one sent without an id gets one. Delivery fees are decimal strings in the store's currency.
- **Texts.** The description, the terms and the legal notice take plain text (a blank line makes a paragraph, a line break a `<br>`) or HTML, sanitised as the editor's own (`toEditorHtml`); blank text is null. The sanitiser (`sanitizeRichTextHtml` from `@louez/utils/sanitize-rich-text`, also applied on read) parses the HTML with `sanitize-html` (htmlparser2) against the editor's allow-list, and it is idempotent: a bare `&`, `<` or `>` is escaped, a character reference already there is kept, a link's `href` stays as written (its scheme is checked on a decoded copy), so a text saved again and rendered again reads the same. Its cost follows the input's length: htmlparser2 pays the depth on each open tag (100 KB of `<b>` takes 76 ms to parse), so `richTextTooDeep` first parses with htmlparser2 itself, counting depth and stopping as soon as it passes `RICH_TEXT_MAX_DEPTH` (256; under a millisecond for a deep input, one linear parse otherwise). The depth counts as sent and once sanitised (a line break the sanitiser turns into `<br />` counts). A write refuses deeper HTML (`TEXT_TOO_DEEP`); the render shows such a value as its visible text alone: htmlparser2's tokenizer gives its text, without attribute values, comments or the content of the elements the sanitiser drops, then that text goes through the sanitiser, so a second pass returns the same string. It cuts nothing: a write checks the sanitised HTML against its TEXT column (65,535 bytes, `TEXT_TOO_LONG`), so what the storefront renders is bounded by what can be stored. Writes parse and sanitise before they take the store's lock (`services/rich-text.ts`); an agent's plain text keeps its `<` and `>` as characters, unless it holds a `<` then a letter later closed by `>`, which reads as HTML (the text fields' descriptions say to write &lt; and &gt;). It runs on the server only: it is not exported from the package's root, the storefront's `RichText` is a server component, a client component renders HTML its server parent sanitised (`RichTextHtml`), and `apps/web/lib/client-bundle-boundary.test.ts` fails when an import from a client module reaches it (it reads directives and imports with the TypeScript 5.9 parser, as TypeScript 7 has no JavaScript parser API yet, and it fails on a client-reachable dynamic load it cannot follow, such as an interpolated `import()`, unless allowed with a reason). A test also checks that `@louez/utils` and sanitize-html load the same htmlparser2. Whether a text shows anything is `hasRichTextContent` (`@louez/utils`), for the API's summaries as for the storefront.
- **One lock.** Every write locks the store row first, then reads the row and writes it back: the `settings` JSON holds every section, so two writes of different sections never lose each other's change. No check reads reservations, so no other row is locked. Every other writer of `settings` or `theme` does the same through `mergeStoreRow` (or `lockStoreRow` inside its own transaction) from `@louez/db`: the onboarding's store step, the launch (`stores.completeOnboarding`), inspections, integrations, customer fields, and the store's own JSON columns beside `settings`: the store's and the customers' notification settings, Review Booster's.
- **Currencies.** A currency is one of `SUPPORTED_CURRENCY_CODES` (`@louez/utils`), the ones the app formats and Stripe charges in; `stores.create` and the onboarding take the same list. Another code is refused before any preview (`CURRENCY_NOT_SUPPORTED`), except the store's own currency sent back unchanged: a store set up in one Stripe no longer takes (HRK) keeps it while it saves the rest, and the company page offers it as a former currency.
- **Reading.** `settings.get` shows the legal texts as a summary (set or not, length, the store's last change); `includeLegalTexts: true` adds the texts themselves.
- **Confirmation.** What customers see or pay at checkout is confirmed with a preview of each value before and after, bound to those values and asked under the lock: a new country or currency, the booking mode or the share paid online, any delivery setting, any tax setting. A write that changes none of them runs directly; text, hours and pickup points never ask.
- **Rules.** Payment mode needs Stripe charges enabled (`STRIPE_REQUIRED`), as the dashboard's dialog said; the shortest rental may not be longer than the longest one; delivery needs the store's coordinates (`STORE_COORDINATES_REQUIRED`). A store has 50 pickup points at most (`LOCATION_LIMIT_REACHED`); one above keeps them.
- **Legal identity.** `settings.getLegalProfile`, `settings.upsertLegalProfile` and `settings.searchCompanyRegistry` (`settings_get_legal_profile`, `settings_update_legal_profile`, `settings_search_company_registry`; `/api/v1/settings/legal-profile`, `/api/v1/settings/company-registry`) hold the store's legal identity (`store_legal_profiles`: legal name and form, SIREN or BCE number, SIRET, VAT number, trade register city, share capital, registered office) and its electronic invoicing switches; the dashboard's invoicing page calls them. An agent looks the company up in the French registry by name, SIREN or SIRET, then saves the profile: two calls. The registry's client is an adapter of the package (`adapters/company-registry.ts`, shared with the checkout's company field); an outage answers `available: false`. A write locks the store row, reads the profile and writes it back merged (absent keeps, null clears an optional field), checked with the dashboard form's schema (`storeLegalProfileSchema`), and marks the store. Only the invoicing switches (`invoicingEnabled`, `vatRegime`, `hasVatOnDebits`) ask a confirmation, as they decide whether Louez sends the store's invoices to the tax network; the identity is text and saves directly. `store.legalProfileUpdated` revalidates the invoicing page and syncs the VAT regime to Super PDP.
- **Billing.** The company marks the store, and every reservation of the store on a new currency; taxes mark every reservation when the rate the dashboard's totals add changes (`beforeTaxRateBps`) ([DL-13](../code-review/04-data-layer.md)).
- **Effects.** Each write emits `store.settingsUpdated` with its section: the app revalidates the section's pages (the business hours every storefront page of the store), and the company and reservation rules notify the platform, as their server actions did.

`dashboard.onlineStore.*` (`routers/dashboard/online-store.ts`, `services/online-store.ts`, the `online_store_*` tools, also in the `settings` bundle, `/api/v1/online-store`) holds the storefront, under the `online_store` domain (an API key made before that domain existed has `none`) and `manage_settings`:

- `online_store.update` is the online store editor's one save: each section it sends (identity, home, contact, legal, seo) replaces what it covers. `online_store.updateAppearance` takes the look field by field: theme, colour, logos, favicon, banner photos and their layout. Both take the store's own images only (`IMAGE_NOT_OWNED` otherwise), and both lock the store row before they patch the `theme` and `settings` JSON. A changed theme invalidates the storefront's cached theme colour (`store.storefrontUpdated`).
- `online_store.createImageUpload` and `completeImageUpload` upload a logo or favicon (`kind: "logo"`) or a banner photo (`kind: "hero"`), as [Uploads](#uploads) describes, and `online_store.uploadImage` does it in one call, with the bytes or a public URL; the dashboard keeps its own file route.
- `online_store.checkSlugAvailability` and `online_store.updateSlug` change the store's web address. Louez keeps no history of former addresses, so a link to the old one stops working once the store is online: the change is sensitive (`destructive`) and its preview shows the old and the new URL and that nothing redirects, bound to the old address and to whether the store is online, both read under the store's lock. A reserved address is refused by the input (`RESERVED_SLUGS`, which holds every first path segment of the app and of the proxy; `apps/web/lib/reserved-slugs.test.ts` walks the app router as Next.js reads it, through route groups, parallel slots and intercepting routes, and fails when one is missing), for a new store too; one taken by another store before the lock answers `STORE_SLUG_TAKEN` with suggestions, and two stores taking the same address at once meet on the unique key, where the second gets the same answer. The slug is in the store's billing snapshot, so the store is marked. The app revalidates the dashboard, the editor and both storefront paths, and drops both addresses' cached theme (`store.slugChanged`). Every event of these writes names the store by the slug its locked row holds, so a rename that committed while a write waited is the one invalidated.

`settings.get` also shows the storefront: its address and URL, tagline, language and look.

## The inbox

`inbox.list` (`inbox_list`, `GET /inbox`) says what needs the store's attention, and `inbox.acknowledge` (`inbox_acknowledge`, `POST /inbox/acknowledge`) marks items as handled (`routers/dashboard/inbox.ts`, `services/inbox.ts`, the `daily` bundle). It is how an agent that cannot be told (MCP has no push across sessions; a bot such as Grok only polls) learns what happened: with the cursor of its last call it gets only what is new. The instructions set no schedule: they say a few minutes between calls is enough if the user asks the agent to keep watch.

- **Items.** Each item is read from where it already lives; nothing is copied, so an item leaves the inbox once what it is about is handled.

  | Type                               | Read from                                                                                     | Shows while                                                                    |
  | ---------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
  | `booking_request`                  | `reservations` pending, not a checkout waiting for its Stripe payment, not a marketplace hold | pending                                                                        |
  | `date_change_request`              | `reservation_activity` `note_updated` with `kind: return_date_request`                        | the request is pending and the reservation confirmed or ongoing                |
  | `pickup_overdue`, `return_overdue` | confirmed past its start, ongoing past its end                                                | the status stays; a pickup on a rental ended more than 30 days ago is left out |
  | `deposit_expiring`                 | `deposit_authorization_expires_at` of an authorized hold, from two days before                | the hold stays authorized on an open reservation                               |
  | `payment_failed`                   | the latest `payment_failed` or `deposit_failed` activity of an open reservation, 30 days back | no rental payment completed since; the deposit still failed                    |
  | `dispute_open`                     | `payment_disputes` open                                                                       | open                                                                           |
  | `unit_conflict`                    | `findConflictingAssignments`, the product page's check, turnover buffer included              | the booking holds that unit                                                    |
  | `overbooking`                      | the `created` activity of a booking made over the stock (`overbooked`)                        | the booking is not over                                                        |
  | `supplier_invoice`                 | `received_invoices` not handled, with Super PDP connected                                     | not handled                                                                    |
  | `einvoice_rejected`                | `invoices` rejected, or failed with no attempt left, 90 days back                             | the status stays                                                               |
  | `billing_gate_closed`              | `readReservationGateSince`                                                                    | the gate is closed                                                             |
  | `store_not_live`                   | the launch checklist, with what it still requires                                             | the store is offline                                                           |
  | `message_not_sent`                 | `api_effects` abandoned, customer messages and store notifications                            | the row is kept (30 days)                                                      |
  | `operation_unknown`                | `api_operations` unknown, or running past its lease, 7 days back                              | its record stays so                                                            |
  | `handoff_waiting`                  | `api_handoffs` active an hour after its link, expired, or failed 7 days back                  | it stays active, or the same step is not started again                         |
  | `invitation_not_sent`              | `api_effects` abandoned, a team invitation's e-mail (`team` read)                             | the invitation is still pending                                                |
  | `image_job_failed`                 | `api_jobs` of an AI photo failed for good, 7 days back                                        | the same photo is not started again                                            |

  Each has a severity, `occurredAt`, one sentence, the reservation it is about, its facts (`details`), the tools that act on it (none when only the user can, in Louez) and `links`.

- **Order and cursor.** Items come in one order: `occurredAt`, then type, then record id (binary). `occurredAt` is when the item became visible here, never earlier than the moment it could first be read, and never a time from outside or typed by a user: a dispute counts from when its webhook wrote its row (Stripe's own date is `details.openedAt`), a closed billing gate from when this instance received the policy in force, or its `effectiveFrom` if later (`details.effectiveFrom`), a late pickup or return from its date or the last change of the reservation's dates or status (`reservations.schedule_changed_at`, set by `changeReservationStatus`, the dashboard's edit and a rental extension: a note or a payment does not count), a deposit from two days before it expires or when its hold was recorded, a booking request from its creation or when its checkout stopped waiting for payment, a unit conflict from when the assignment, the booking's dates and status, the retirement or downtime and, when they make it, the store's availability rules were all as they are (`stores.availability_rules_changed_at`, set by the reservation rules' write when the turnover buffer or the pending rule changes). Items show 30 seconds after they happen, on the database's clock, so a row committed after a call is not passed over. The cursor is the last position read; without more to read, the next cursor stands at that horizon. A call is read-only: the same cursor gives the same items, minus those handled since. An item that comes back, or whose cause changes again (a new failure, a late reservation's dates edited), keeps its id with a later `occurredAt`.
- **Pages.** Up to 100 items a call. Each source reads at most a page and one row in that order, with the store's indexes (`reservations_store_status_end_idx` for the open reservations), so a call costs one query per type the caller may see, with no N+1.
- **Rights.** It opens to a caller who may read reservations, settings or integrations (`anyOf`). Each type shows only to a caller who may read what it shows: payment items need payments, a unit conflict and a failed photo job products, a supplier invoice integrations, the gate and the launch settings. Without customers, no name, no customer's own words. An operation shows to the connection that made it, and to a dashboard session every operation of the store. A connection over several stores calls it once per store, with `storeId`.
- **Acknowledging** is per store, not per connection: the cursor already tells each poller what it has seen, while an acknowledged item is handled for the team, so two agents do not tell the owner the same thing twice and the dashboard can show the same list. `inbox_acknowledgements` holds the occurrence (type, record, `occurredAt`) and who marked it; the same record coming back with a later `occurredAt` shows again. Each item must be in the store's inbox now, with its `occurredAt`, read by the list's own queries for those records. The call marks those and returns the others in `rejected`, each with `currentOccurredAt`: the occurrence the inbox holds now for the item, or null when it left the inbox (an unknown id, another store's item, an item handled meanwhile). A batch is accepted in part rather than refused whole, so an agent working from an old list keeps what still holds and learns what to drop or send again; inbox_list without a cursor starts it again from what the inbox holds. A store's marks are written one call at a time, under the store row's lock. It opens to a connection that may write reservations, payments, settings or integrations, and each item needs write access to its first domain; marking twice changes nothing. A store keeps its latest 2,000 marks (the oldest go first), and the cron deletes marks older than 90 days: an item still open then shows again.

## Handoffs

Some steps only the human can take: Stripe's identity checks, typing a card. A procedure that needs one hands it over (plan, section 7): it returns a link to a Louez page, the agent gives it to the user, then reads the handoff until it is done. `services/handoffs.ts` holds the logic, `api_handoffs` (migration 0096) the rows, `apps/web/app/handoffs` the pages.

- **Kinds.** Each kind is started by its own domain's procedure, with that domain's rights: `payments_start_stripe_onboarding` (`stripe_connect_onboarding`) and `payments_open_stripe_dashboard` (`stripe_dashboard`) need `settings` write and `manage_settings`, in the `settings` bundle; `billing_start_card_setup` (`billing_card_setup`) needs `billing` write and `manage_settings`, and only the owner of a store the billing service bills may start it (`CARD_SETUP_UNAVAILABLE` says why not), in the `billing` bundle; `team_invite_member` from an agent (`team_invitation`) needs `team` write and `manage_members`, in the `team` bundle ([The team](#the-team)). `handoffs_get` (`GET /handoffs/{id}`, `daily` bundle) reads one, with read access to its kind's domain: settings for Stripe, billing for the card, the team for an invitation's approval; any of the three opens the procedure, and the handoff's own kind decides.
- **The link.** `/handoffs/<token>`: the handoff's id then a 43-character secret, with no dot (the proxy takes a dotted path for a static file). Only the secret's SHA-256 is stored. It works for 24 hours, for the user the requesting connection acts for. The answer that holds it declares `secretOutput`: never stored, never replayed, and `handoffs_get` never gives it again. On MCP the tool's text puts it on a line of its own, with the id to poll.
- **One active per kind and subject.** A store has at most one handoff of a kind and subject pending or opened (`active_slot`, unique with the store, the kind and `subject`, migration 0099). The subject is empty for a store-wide step (Stripe, the billing card); a team invitation's is its address's SHA-256, so each address has its own approval. Asking again gives the same handoff a new link and voids the old one, so an expired step resumes; another user asking starts it over for them. Writes are serialized by the store row's lock.
- **Opening.** The page needs a session: signed out, the user goes through `/login` and back, the handoff path kept meanwhile in a short-lived cookie scoped to `/handoffs` (`/handoffs/resume` reads it), never in the login page's URL. It shows the step only to the link's user, while their role still allows it (`manage_settings` for Stripe, owner for the card) and the connection that asked for it still exists, and otherwise says why (another account, an expired or replaced link, a finished step). Loading it changes nothing, so a link preview starts nothing. The user continues with a form posted to `/handoffs/<token>/continue`, same-origin only; the handoff is then `opened`, with a fresh state, and the user goes to the provider.
- **Attempts.** Each click starts an attempt, named by its state (`return_state_hash`); a new click, or another user taking the step over, drops the earlier attempt's provider flow (`provider_ref`) and lease. Every write that belongs to an attempt (its return's claim, its Checkout, its completion or failure) is one conditional statement on that attempt, and so is the replacement: InnoDB orders them, and once an attempt is replaced its late writes change nothing. A return checked before a new click, or a Checkout of an earlier click, never completes the new attempt.
- **Provider checks.** A provider call for an attempt first takes a lease on the database's clock (`provider_check_at`), only when it is free: a return (its claim takes it), or a check (`handoffs_refresh` on a billing card Stripe has not confirmed yet) while the link has not expired. The lease is 30 seconds, doubling with each check, 5 minutes at most; concurrent returns and polls, and those within it, read the stored status without calling the provider. A valid return after the link expired still completes the step (the user finished on the provider's page), under the same lease.
- **The provider's return.** `/handoffs/return/<id>/<state>` and, for an expired Stripe link, `/handoffs/refresh/<id>/<state>`. The state is in the path (the billing service takes a return URL without a query and adds `?checkout=`); only the latest click's state, for the link's user still allowed, counts. The outcome is read from the provider, never from the URL. Then `/handoffs/done/<id>` says the step is done ("go back to your agent"), not finished, or failed.
- **Completion.** Stripe's onboarding completes once the account's details are submitted: on the return, on `payments_sync_stripe_status`, on the dashboard's own callback, or on the `account.updated` webhook; charges may still wait for Stripe's review, which `payments_sync_stripe_status` shows. Stripe's dashboard completes once the user is on their way. The billing card completes when the billing service saved it; a card Stripe has not confirmed yet is asked again by `handoffs_refresh`, within the provider-check lease. `handoffs_get` only reads: it answers `confirming: true` for such a card. Settling is a write (it may save the card, replacing the one on file, and calls the billing service), so it is its own tool, with write rights on the step's domain, rather than a read that ChatGPT would have to treat as destructive on every poll. A failure Louez can name (no email for Stripe, the step no longer available, the connection revoked) ends it `failed` with its code; a provider that did not answer lets the user try the same link again.
- **Status.** `pending`, `opened`, `completed`, `failed`, and `expired` (an active one past its link's expiry, not stored).
- **Inbox.** `handoff_waiting` shows a handoff active an hour after its link went out, expired, or failed in the last 7 days and not started again; each to who reads its kind's domain (Stripe: settings; the card: billing; an invitation's approval: the team), and is acknowledged with write access to that domain. Its tools are `handoffs_get` and the tool that gives a new link, and first `handoffs_refresh` for a card Stripe has not confirmed yet. A closed billing gate lists `billing_get_status` and, unless the store is suspended, `billing_start_card_setup`.
- **Revoked connections.** Revoking the API key or the agent connection that asked for a step ends its active handoffs (`failed`, `connection_revoked`), and a link of a connection that no longer exists opens nothing. Better Auth's consent endpoints (`/oauth2/get-consent`, `get-consents`, `update-consent`, `delete-consent`) are turned off (`AUTH_DISABLED_PATHS`): a consent deleted behind Louez's grant would leave the grant and its links standing. Its client endpoints refuse every session already (`clientPrivileges`). A client revoking its own token (`/oauth2/revoke`) signs itself out; the user's grant, and the steps it handed over, stand until the user revokes it.
- **Privacy.** The URLs hold secrets. The proxy marks the handoff routes (`x-louez-handoff`, refused from a visitor), so the root layout loads no PostHog, Umami, fromHello or client log drain on them; their pages and redirects send `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. Logs redact the link's secret and the return's state with one set of patterns (`platform/redact.ts`): evlog applies them to every event before it prints it or drains it (`redact`, set in `apps/web/lib/evlog.ts` once the logger is locked), and a provider error is logged as one redacted line (`logProviderError`), never as the error object, whose request a provider may echo. The development request log leaves the paths out.
- **Retention.** The cron deletes handoffs untouched for 90 days, oldest first, in batches of 500 within 5 seconds a run (`api_handoffs_updated_idx`); deleting an account deletes its stores' handoffs.

The dashboard keeps its direct flows (it sends the browser to Stripe at once) over the same services: `startConnectOnboarding`, `syncConnectStatus` (the settings' sync button calls `payments.syncStripeStatus`), the dashboard link, and `writeConnectColumns` for every write of the Connect columns, the webhooks' included, which marks the store's billing snapshot.

## Billing

`billing.getStatus` (`billing_get_status`, `GET /billing`) reads what the billing pages show, read-only, through `ports.billing`: who bills the store (`none`, `legacy`, `service`), the plan in force and a change waiting for the period's end, the offer and the service's notice in its words, Louez's pay-as-you-go ladder and this month's figures, the card, the month-end invoices, the billing service's month and unpaid balance (or `reachable: false`), the card gate (`readReservationGateSince`, as the inbox reads it) and whether `billing_start_card_setup` can run for the caller. Amounts are decimal strings. It needs `billing` read and `manage_settings`, as the plan actions do. Changing or cancelling a plan stays in the dashboard.

**Not for OpenAI's clients.** OpenAI's plugin guidelines (https://developers.openai.com/plugins/plugin-guidelines, "Commerce and monetization", read 2026-11-09) allow commerce for physical goods only: a plugin may not sell digital services, "display subscription plans, initiate new subscriptions, or promote upgrades", nor "link directly to a checkout or other transactional page". The billing tools read the store's Louez plan, offer and fees, and open the Checkout of the card Louez charges, so an OpenAI client (ChatGPT and Codex share the directory) never reaches the `billing` domain, whatever its grant (`clientWithholding`, `platform/agent-clients.ts`). It is told apart by its metadata document (`CHATGPT_CLIENT_ID`) or, registered dynamically, by its declared name (ChatGPT, OpenAI, Codex): a name another client copies only takes tools away from it. This is the directory's policy for recognised OpenAI clients, not a security boundary: a client that registers itself picks its own name. The consent page and each call read the same thing, the client id and the whole registered name (`registeredName` of the grant), never the name cut to 100 characters for the audit. Its credential has `billing` at `none` and the `billing` bundle left out, so the tools are never listed and a call answers `NOT_AVAILABLE_TO_THIS_AGENT` (no grant changes it, so nothing to ask the user to enable); the consent page and the editor do not offer the bundle, the instructions never name it nor the billing card, and the inbox's closed billing gate lists no tool for a caller that may not read billing, only the billing page's link. No answer prompts it to buy anything from Louez either (`ClientWithholding.purchases`): out of AI credits, a photo tool says so, with no recharge link. The user manages billing in Louez.

Nor does an OpenAI client create stores, not even through a link (product owner's decision, 2026-11-10): a new store starts a billing relationship with Louez. Its withholding also covers the `stores` domain, whose only agent procedure is `stores.create`, so `stores_create` is never listed and a call answers `NOT_AVAILABLE_TO_THIS_AGENT` before any other refusal. With no store, `stores_list`'s `hint` and the instructions say "This user has no store yet. Ask them to create it in Louez, then continue here." (`NO_STORE_ASK_USER`), with no URL to the onboarding, and the instructions leave `stores_create` out of the address checks. Every other client keeps `stores_create` as it is.

## The team

`dashboard.team.*` (`routers/dashboard/team.ts`, `services/team.ts`, the `team_*` tools of the `team` bundle, `/api/v1/team`) is the dashboard's team page. Roles are `owner` and `member` (`packages/utils` permissions): a member reads and writes the store's data, an owner also deletes, manages the settings and the team (`manage_members`).

- **Reads**, for every member and any connection with `team` read: `team.listMembers` (`team_list_members`, `GET /team/members`: name, e-mail, avatar, role, when they joined, newest first, and `memberLimit`, the store's team-member allowance, owners not counted, from `ports.team.collaboratorLimit`) and `team.listInvitations` (`team_list_invitations`, `GET /team/invitations`: the pending ones, with the address, the role, when sent, the expiry and `expired`). Both page with a cursor (100 at most) and carry the team page's link. An invitation's token or link is never in an answer.
- **Invite** (`team.invite`, `team_invite_member`, `POST /team/invitations`), for an owner, from the dashboard or an agent (Téo's decisions, 2026-11-09). The input takes the address and, optionally, `role: "member"`: no other role validates, so nothing here makes an owner. Under the store row's lock: the store's team-member limit (`TEAM_LIMIT_REACHED`, "This store has reached its team-member limit. No invitation was created.", for every client: no plan, no way to buy more), no pending invitation of the address, whether or not it has an account (`TEAM_INVITATION_ALREADY_SENT`), not a member already (`TEAM_ALREADY_MEMBER`). Then someone with a Louez account joins at once (`outcome: "added"`, no e-mail; any pending invitation of theirs is cancelled), anyone else gets an invitation valid 7 days (`outcome: "invited"`). The e-mail goes through the outbox (`team.invitationEmail`): its row holds the invitation's id, never its token, and the sender reads the address and the token when it sends, so a cancelled, accepted or expired invitation sends nothing and one sent again links its new token. An instance without e-mail queues nothing and answers `invitationEmail: "not_configured"`; the dashboard then copies the link from `team.invitationLink`. The platform's notice (Discord, fromHello) is `team.memberInvited` on `afterCommit`.
- **An agent's invitation is approved by an owner.** From a key or a token, `team_invite_member` creates nothing: it runs the same checks, then records an approval, a `team_invitation` [handoff](#handoffs) bound to the store, the address, the role and whether the address joins at once, and answers `outcome: "approval_requested"` with its link (`secretOutput`). The user approves the invitation from the link: `/handoffs/<token>` shows the address, the role, whether they join at once, and that they will see the customers, reservations and payments, with Approve and Decline. The page posts to `/handoffs/<token>/decide`, which calls `team.decideInvitation`, an account procedure for a session only, as the link's user still allowed to manage the team; no agent reaches it on any transport, and no confirmation token can grant access. Approving runs the invitation above and completes the handoff in the same transaction, under the store's lock, while the link is still current; declining ends it `failed` (`declined`). An invitation that can no longer go out as shown ends it too, with why: the address got an account since (`TEAM_APPROVAL_CHANGED`, `request_changed`), a membership or an invitation (`request_changed`), the seats are full (`limit_reached`), the day's e-mails are spent (`email_limit`); the page then sends the owner to the approval's result, which says why and that the agent asks again. `handoffs_get` gives the agent the outcome, with `team` read alone; an approval waiting an hour, expired or failed is a `handoff_waiting` item. The same address asked again gets the same approval with a new link; links last 24 hours.
- **Caps.** At most `MAX_OPEN_INVITATION_APPROVALS` (10) approvals open per store (`TEAM_APPROVALS_FULL`), counted under the store's lock both for a new approval and for an expired one asked again: each waits for an owner's click, and a store hiring a crew asks for a handful. At most `INVITATION_EMAILS_PER_DAY` (20) invitation e-mails per store in 24 hours, sends again included, counted from the outbox on the database's clock (`TEAM_INVITATION_EMAIL_LIMIT`, retryable): plans allow a few members, and the cap bounds what one store can make Louez's sender mail to strangers.
- **Accept** (`team.acceptInvitation`, a session-only account procedure, from `/invitation/<token>`). It reads the invitation's store, takes the store row's lock as every team write does, then reads the invitation again under it, locked: still pending with this token, in time, for the signed-in address, not a member already, and a seat left for a member. It consumes the invitation with a statement that changes it only while it is still so, then adds the membership: a cancellation or a removal committed meanwhile wins. The store becomes the user's active one.
- **Remove a member** (`team.removeMember`, `team_remove_member`, `DELETE /team/members/{id}`) and **cancel an invitation** (`team.cancelInvitation`, `team_cancel_invitation`, `POST /team/invitations/{id}/cancel`), for an owner. An owner is never removed (`TEAM_OWNER_NOT_REMOVABLE`), so a store always keeps its owner, and nobody removes themselves (`TEAM_CANNOT_REMOVE_SELF`). A removed member loses access on their next call, connections included, and their pending invitations to the store are cancelled, so no earlier link lets them back.
- **Confirmations.** Removing and cancelling always ask an agent, with `always`, even a connection whose confirmations are off: each takes a person's access to the store's data away, and an agent cannot undo it on its own say. The preview names the person (the address, and the name when they have an account) and the role, asked under the store's lock; the token is bound to them.
- **Inbox.** An invitation e-mail the outbox abandoned, for an invitation still pending, is an `invitation_not_sent` item, for who reads the team: it names the address, never the link, with the team page's link.
- **The dashboard only** (`actors: ["session"]`): sending an invitation again (`team.resendInvitation`: a new token, 7 more days, the e-mail again) and reading its link (`team.invitationLink`), as the link is the invitation's credential. No procedure changes a role. An agent gives the user the team page's link for these (the server's instructions say so).

## OAuth for agents

Claude.ai, ChatGPT and other MCP clients connect by signing in to Louez, without a key. Louez is the authorization server (Better Auth's `@better-auth/mcp` plugin over its OAuth 2.1 provider) and `/api/mcp` the protected resource. The plugins are set in `packages/auth/src/oauth.ts`.

### The flow

1. The client calls `/api/mcp` without a token. The answer is a 401 with `WWW-Authenticate: Bearer resource_metadata="<app>/.well-known/oauth-protected-resource/api/mcp"`.
2. It reads that document (resource `<app>/api/mcp`, authorization server `<app>/api/auth`), then `<app>/.well-known/oauth-authorization-server/api/auth`. The app's `/.well-known/*` routes hand these paths to Better Auth, which answers them before routing; `/api/auth/.well-known/openid-configuration` is served too.
3. It identifies itself. A Client ID Metadata Document (CIMD, the `cimd()` plugin, MCP 2026-07-28 profile) is the preferred way: the `client_id` is an HTTPS URL that Louez fetches with a resolve-once, private-address-refusing transport. Dynamic client registration (`/api/auth/oauth2/register`) stays open for clients that only know it, restricted: the standard scopes and the MCP resource only, no client-credentials grant, rate limited. No session may manage clients or resources (`clientPrivileges` and `resourcePrivileges` refuse), and the session JWT endpoint of the JWT plugin is off.
4. The browser goes to `/api/auth/oauth2/authorize`. Signed out, it lands on the usual `/login` with a signed query; every sign-in method then goes back to the authorization endpoint (`util.oauth-authorize-url.ts`). Signed in, it lands on the consent page, `/oauth/consent`.
5. The consent page shows who asks without vouching for it: the name the client declared, who declared it (the host serving its metadata document, or "registered dynamically"), and the host of this request's `redirect_uri`, the one Better Auth checked and signed, where the code goes; a loopback redirect gets a warning, as any local program can receive it. "Vérifié" is only for a client id on `VERIFIED_CLIENT_IDS` (`services/agent-grants.ts`): Claude's two metadata documents and ChatGPT's, each documented by its publisher and redirecting only to its own host. Claude Code's is left out: its code goes to a loopback address any local program can take. A client from a metadata document shows the website icon of its client id's origin (`/favicon.ico`, else the home page's icon links), fetched by Louez through the CIMD transport within 10 seconds, 8 lookups at most at once, with a 100 KB cap, raster only, kept in memory a day (a missing one an hour) and served from `/api/agent-connections/client-icon` to signed-in users; a client that registered itself keeps a generic tile, as the logo it declares could copy another client's. Then the terms below. Accepting calls `dashboard.agentConnections.authorize`: the grant is saved first, then Better Auth records its consent and issues the code. Refusing sends `access_denied` back.
6. The client exchanges the code (PKCE) for an access token bound to the resource, a JWT signed by the JWT plugin (`at+jwt`, one hour), and a refresh token (`offline_access`).

The issuer and the resource come from `AUTH_URL`'s origin, even where the development base URL follows the request host: a token names one issuer. OAuth needs HTTPS (plain HTTP on a loopback host only); an instance on plain HTTP serves no OAuth and keeps API keys.

### Grants

A grant (`api_agent_grants`, one per user and client, linked to the client and the user like Better Auth's consent) holds what the user accepted:

- **Stores**: one, several (`api_agent_grant_stores`), or all of the user's stores, current and future ones.
- **Rights preset**: `read` ("Lecture seule": read on every domain) or `write` ("Lecture et modification": write on every domain, analytics staying read-only). The member's role still cuts it down.
- **Confirmation**: "Demander une confirmation avant les actions sensibles", on by default (`confirmSensitive`). Its description says what it does not cover: recording, returning or deleting a payment, spending AI credits, removing a member and cancelling an invitation ask whatever it says ([Sensitive operations](#sensitive-operations)).
- **Tool bundles**: `daily` by default; the others are opted in, among those that hold a tool ([Stores, tool bundles and instructions](#stores-tool-bundles-and-instructions)).

Creating, changing and revoking a grant are session-only account procedures (`dashboard.agentConnections.*`, `actors: ["session"]`), recorded in `api_operations` on the account scope, so a user with no store yet can connect an agent. The consent page then offers only "all my stores, including the next ones", says the agent can create the store with "Read and edit" rights, and the grant reaches every store the user creates later, the agent's own included. A store granted before that the user can no longer open is dropped from what the page and the connection editor start from (a user left with no store reconnects over every store to come); the procedures refuse such a store with `AGENT_CONNECTION_STORE_INVALID` and change nothing. "Agents connectés" on Settings > Integrations > MCP lists the grants with their stores, preset, bundles, last action (the last write in `api_operations`) and creation date. Revoking deletes the grant; its consent and its tokens go with it (see below), so the next authorization asks again.

### The access token on each call

`resolveAccountActor` takes a bearer that is not `lz_…` as an access token, on MCP only (OpenAPI takes keys, RPC sessions). It is verified in full: signature against the JWT plugin's keys (read in process, cached five minutes), issuer, audience (the MCP resource), expiry, type `at+jwt`, `azp`; a DPoP-bound token is refused. Then the grant of that user and client is read again, with its client, which must not be disabled. Each access token names the grant it was issued under (`louez_grant`), and the grant read must be that one.

A token lineage is bound to its grant, not to the user's current one. The grant id is Better Auth's consent reference (`postLogin.consentReferenceId`, read when the authorization starts): the provider stores it on the consent, the code and every refresh token, and carries it to each token refreshed from them. The claim is that reference; issuing a token for a reference whose grant is gone fails with `invalid_grant`, and for JWT access tokens the claims are made before the refresh token rotates, so a refused refresh leaves nothing behind. In the database, `reference_id` on `oauth_consents`, `oauth_refresh_tokens` and `oauth_access_tokens` is a foreign key to `api_agent_grants.id` with `ON DELETE CASCADE`: revoking (deleting the grant) deletes its consent and its whole token lineage in the same statement, and a rotation that inserts its new row after the revoke fails on the key (InnoDB locks the parent row for the child insert, so the two serialize). An unused code from before a revoke is refused at the exchange. A replayed old refresh token no longer exists, so it never triggers the provider's family invalidation, which would otherwise delete every refresh token of the user and client, the new grant's included. Grant ids are never reused, so a deleted grant is its own tombstone. Anything that fails is `UNAUTHENTICATED`; nothing falls back to another credential.

**Retention.** An access token lasts an hour and a refresh token 30 days, Better Auth's defaults; the access tokens for the MCP resource are JWTs and are never stored. The privacy policy promises a stored access or refresh token is deleted at most 7 days after it expired or was revoked: the cron deletes it after 6, so a backlog or an outage of up to a day still keeps the promise, and a used client assertion (`oauth_client_assertions`, which refuses a replayed `jti`) an hour after it expired, on the database's clock (`purgeOAuthTokens`, `packages/auth/src/oauth-retention.ts`, every minute). Each table has its own 2 seconds a run, so a backlog in one never holds the others back; a batch reads up to 500 due ids without locking (the dates have no index, and the plain read never blocks a sign-in or a rotation), then deletes them by primary key with the condition checked again. Two runs at once only race to delete the same ids. A valid token is never deleted. A rotated refresh token is revoked: replayed within those 6 days, before its expiry, it still revokes its family; once deleted, it is an unknown token, `invalid_grant` without touching the family. Deleting a refresh token deletes the access tokens issued with it (`refresh_id`), expired by then. The grant stays.

Known limit, in Better Auth 1.7.18 itself: a refresh replay already in flight when the grant is revoked (read before the revoke, sent after a reconnect, outside the provider's 30-second reuse window) reaches the provider's family invalidation, which deletes every refresh token of the user and client, the new grant's included. It grants nothing, and the agent signs in again; it needs a stolen, already-revoked refresh token. Fix upstream: scope `invalidateRefreshFamily` to the token's `referenceId`. A refresh that loses the race against a revoke also answers 500 with an empty body instead of `invalid_grant`.

The credential is `kind: "oauth"`, its id the grant id, its client name the OAuth client's, its scopes the preset's, `confirmSensitive` the grant's. `storeId` is set when the grant covers one store; otherwise `stores` lists the granted ones (null for all) and the caller names one, as in [Stores, tool bundles and instructions](#stores-tool-bundles-and-instructions). The member's role in that store is read on every call, so a removed member is refused. A platform admin gets no staff powers through a token.

### Connect from Claude, Claude Code and ChatGPT

What Anthropic's connector directory and OpenAI's plugins ask of the authorization server (checked 2026-11-09), and the URLs each client uses. Better Auth 1.7.18 does all of it with the plugins above; `packages/auth/src/oauth.test.ts` runs the four published client documents through the flow and pins each point.

**The server, for every client**

- [ ] The URL the user enters is `https://app.louez.io/api/mcp`, exactly: it is the `resource` of the metadata, and Claude compares the two as strings.
- [ ] Without a token, `/api/mcp` answers 401 with `WWW-Authenticate: Bearer resource_metadata="https://app.louez.io/.well-known/oauth-protected-resource/api/mcp"`; a bad token adds `error="invalid_token"`.
- [ ] That document lists one authorization server, `https://app.louez.io/api/auth` (Claude uses the first only). Its metadata is at `https://app.louez.io/.well-known/oauth-authorization-server/api/auth` and `https://app.louez.io/api/auth/.well-known/openid-configuration`.
- [ ] The metadata says `code_challenge_methods_supported: ["S256"]` (PKCE is required, `plain` refused), `client_id_metadata_document_supported: true`, `none` and `private_key_jwt` (with the client secrets) in `token_endpoint_auth_methods_supported`, `offline_access` in `scopes_supported`, and `authorization_response_iss_parameter_supported: true`. No document offers DPoP: Better Auth always lists `dpop_signing_alg_values_supported`, and `withoutDpopMetadata` (`oauth.ts`) takes it out, as `/api/mcp` takes bearer tokens only.
- [ ] Every redirect back to the client carries `iss=https://app.louez.io/api/auth` (RFC 9207): the code, `access_denied`, and the errors after the redirect URI is checked (`invalid_request`, `invalid_scope`, `invalid_target`, `login_required`). A request whose client or redirect URI is not known never goes back to it: its error stays on Louez.
- [ ] The token endpoint takes `application/x-www-form-urlencoded`. The access token's `aud` holds the `resource` the client sent; another resource is `invalid_target`, and `/api/mcp` refuses a token for another audience or issuer.
- [ ] Requests from the ranges Anthropic and OpenAI publish (`packages/auth/src/provider-egress.ts`, with its sources: Anthropic's `160.79.104.0/21` and `153.61.208.0/20`, OpenAI's `chatgpt-connectors.json`) get higher ceilings per address: 600 a minute for the token endpoint and each discovery document, 300 for UserInfo, 60 for registration. Every other address keeps the usual ones: 20 token requests, 5 registrations, 60 UserInfo calls and 100 discovery fetches a minute. The authorization endpoint keeps its 30 for everyone, as the user's browser opens it. Only a declared ingress raises a ceiling: with `TRUSTED_PROXY=cloudflare`, a valid `cf-connecting-ip` decides, and nothing else does. Unset (the default), or with that header missing or malformed, every address keeps the usual limits, whatever `true-client-ip`, `x-real-ip` or `x-forwarded-for` say. Better Auth still counts under the first valid one of `cf-connecting-ip`, `true-client-ip`, `x-real-ip` and a single-address `x-forwarded-for` (`authIpAddressOptions`), so an elevated request is counted under the Cloudflare address it was elevated for.
- [ ] Production sets `TRUSTED_PROXY=cloudflare`, and only once the origin accepts traffic from Cloudflare alone (Cloudflare's addresses, or an authenticated origin pull): any request that reaches it directly can write its own `cf-connecting-ip`. Self-hosted instances leave it unset.
- [ ] A refresh rotates the refresh token. A retry within 30 seconds gets the same answer; after that, the spent token is `invalid_grant` and revokes its family. An unknown, altered or other client's token is `invalid_grant` too.

**Claude (claude.ai on the web, Desktop, mobile, Cowork)**

- [ ] Client id `https://claude.ai/oauth/mcp-oauth-client-metadata` (public, PKCE), or `https://claude.ai/oauth/mcp-oauth-client-metadata/confidential_client` (`private_key_jwt`, keys at `https://claude.ai/v1/mcp/jwks`). Nothing to register; the consent page shows "Vérifié".
- [ ] Redirect `https://claude.ai/api/mcp/auth_callback`, matched exactly.
- [ ] Requests come from `160.79.104.0/21`.

**Claude Code**

- [ ] `claude mcp add --transport http louez https://app.louez.io/api/mcp`, then `/mcp` to sign in.
- [ ] Client id `https://claude.ai/oauth/claude-code-client-metadata` (public). Its redirects `http://localhost/callback` and `http://127.0.0.1/callback` match on any port (RFC 8252); the host, path and scheme must match. Any client with a registered loopback redirect gets the same rule, and only on loopback.
- [ ] The consent page warns that the code goes to a local address and does not show "Vérifié".

**ChatGPT (and Codex)**

- [ ] Client id `https://chatgpt.com/oauth/client.json`, authenticating with `private_key_jwt` (keys at `https://chatgpt.com/oauth/jwks.json`, fetched through the CIMD transport). The consent page shows "Vérifié".
- [ ] Redirect `https://chatgpt.com/connector_platform_oauth_redirect`: the stable one, as Louez returns `iss`. If the builder picks dynamic registration, ChatGPT registers its own client with `https://chatgpt.com/connector/oauth/{callback_id}`, accepted like any HTTPS redirect.
- [ ] ChatGPT asks for the advertised scopes (`openid profile email offline_access`); the UserInfo endpoint gives the user's e-mail and `email_verified`, which an Enterprise workspace checks against its domains.

**Known limits**

- Better Auth counts per address and has no option for another key, so the platform ceiling applies to each address of a range, not to the range as a whole, and a connection cannot be counted on its own `client_id`. A counter per range or per client needs a limiter of Louez's own in front of these routes.
- Better Auth's counters read those headers as the visitor sent them when Cloudflare did not set the first one, so a request that reaches the origin directly can pick a new counter each time, on every limit of `/api/auth`, not only these. Only an origin closed to all but Cloudflare prevents it.
- The ranges are copied, not fetched: refresh `provider-egress.ts` from its two sources when they change. An address a platform stops using keeps the higher ceiling until then; a new one gets the usual limits.
- A client that sends a DPoP proof to the token endpoint anyway gets a DPoP-bound token, which `/api/mcp` refuses. Neither Claude nor ChatGPT does.

## Directory plugins

The packages that list Louez in the assistants' directories (OpenAI's Plugin Directory for ChatGPT and Codex, Anthropic's connector directory, Cursor's marketplace for Grok) live in the public MIT repository [Synapsr/louez-assistant-plugins](https://github.com/Synapsr/louez-assistant-plugins), not here: manifests, texts, logos, skills, the reviewers' test cases and the script that builds each upload. They all point at `https://app.louez.io/api/mcp`; what a directory's client sees is decided here ([Billing](#billing), `platform/agent-clients.ts`), so a test case may only name a tool listed for that client.

**OpenAI's domain check.** Before it connects the MCP server, OpenAI's plugin portal (platform.openai.com/plugins, MCPs > Connect) shows a token and reads it at `https://app.louez.io/.well-known/openai-apps-challenge`. `apps/web/app/.well-known/openai-apps-challenge/route.ts` serves `OPENAI_APPS_CHALLENGE` there: the token alone, trimmed, as `text/plain; charset=utf-8` with `Cache-Control: no-store`, read at request time (`connection()`), so setting it in the deployment's env needs no rebuild. Unset, empty, longer than 512 characters or holding whitespace, the route answers 404 (`apps/web/lib/openai-apps-challenge.ts`). The token is public, not a secret; set it in Infisical (`/web`, `prod`) and Easypanel, then press Verify in the portal. The proxy lets the path through untouched on every host (`apps/web/proxy.test.ts`).

**A new review for each package.** OpenAI rescans the MCP server every day: a new or changed tool reaches users once its scan passes, with no new upload. Anything in the package (name, texts, logos, test cases, release notes, skills) is read only from the ZIP: changing it means a new ZIP with a higher `version`, and a new review. The MCP server's URL cannot change once submitted. Reviewer credentials go in the portal (Review details), never in the ZIP.
